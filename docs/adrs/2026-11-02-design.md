# paseo-playbooks: design

Status: design complete, pending approval. No code yet.

## 1. Split of responsibilities

One Paseo agent, the **Playbook Manager**, runs a playbook. Each step runs as one of
its subagents in the same workspace. That workspace is a Paseo worktree dedicated to the
run, so a run never touches the repository's main checkout.

| Plugin (deterministic)                                        | Manager agent (judgment)                                 |
| ------------------------------------------------------------- | -------------------------------------------------------- |
| Loads and validates playbook YAML from the workspace folder   | Picks the playbook that fits the request                 |
| Persists run state on the daemon volume                       | Writes each step's brief from the request and past steps |
| Computes ready steps from `needs`, resets on loops, limits    | Reads each step's result and chooses the outcome         |
| Creates step subagents with role, prompt and labels           | Decides whether to retry, loop or escalate               |
| Detects when a step agent finishes and wakes the manager      | Summarises the run for the human at a gate               |
| Records gate decisions from the panel                         | Relays gate decisions arriving by chat (Slack later)     |
| Renders the two right-hand panels                             |                                                          |

The manager never edits run state directly. It calls the plugin's tools, and the plugin
refuses any transition the playbook does not allow.

```text
 request (Paseo UI now, Hub/Slack later)
            │
            ▼
   Playbook Manager agent ──tools──▶ plugin (daemon subprocess)
            ▲                          │  ├─ playbooks: <workspace>/.paseo/plugins/playbooks/
            │ wake-up prompts          │  ├─ runs: $PASEO_HOME/plugin-data/paseo-playbooks/runs/
            │                          │  └─ creates step agents (parent = manager)
            │                          ▼
            └──────────── step subagents (same workspace) ── report_step_result
```

## 2. Where playbooks live

Playbooks are **per workspace**. The plugin reads them from the manager's workspace
folder (the workspace's `directory`), so a worktree or branch carries its own playbook
changes, and you can test an edit in a worktree before merging it. Each repository uses
this layout, as in Ansible:

```text
<workspace folder>/.paseo/plugins/playbooks/
├── defaults/
│   └── main.yaml              # optional: repo-wide agent defaults
├── pr.yaml                    # one playbook per file; the file name is its ID
├── release.yaml
└── roles/
    ├── investigator/
    │   ├── role.yaml          # title, readonly, agent
    │   └── instructions.md    # the role's system prompt
    ├── implementer/
    ├── reviewer/
    ├── local_qa/
    └── babysitter/
```

- Every `*.yaml` file at the top level is a playbook. As in Ansible, playbooks sit next
  to `roles/` with no subfolder. Shared settings live in subdirectories (`defaults/`,
  `roles/`), so no file name is reserved.
- A playbook refers to a role by its directory name (`role: reviewer` →
  `roles/reviewer/`). A role can serve several playbooks.
- The Playbooks panel shows this workspace's playbooks. A broken role shows as an error
  on every playbook that uses it.
- `start_playbook` stores a copy of the resolved playbook with its roles and defaults in the
  run, so editing the files does not change runs already in progress.

### One worktree per run

Steps share one checkout, and the Implementer switches branches and pushes. To keep that
away from the main checkout and from other runs, every run lives in its own Paseo worktree
workspace:

- **Start in the Playbooks panel** creates a worktree workspace that branches off the
  current workspace (`paseo.workspaces.create({ source: { kind: "worktree", action:
  "branch-off", … } })`), starts the manager in it, and opens it. The new worktree has
  the same playbook files, because it branches from the same commit.
- **The worktree branch is the PR branch:** Start names it
  `playbooks/<playbook>-<runId>`, for example `playbooks/pr-7f3k2`. The Implementer
  commits and pushes on it, and loops push to the same branch, so one run means one
  worktree, one branch and one PR.
- **The manager's agent settings** come from an optional `manager:` block in
  `defaults/main.yaml` (`provider`, `model`, `mode`). They fall back to the `agent`
  defaults, then to Claude Opus in `default` mode. The manager never edits files, so
  `default` mode is enough. Its mode is also subject to the daemon cap.
- **`start_playbook` refuses** when the manager's workspace is not a worktree
  (`workspaceKind !== "worktree"`), with a message saying to start from the panel. Later,
  the Hub trigger will target a worktree.
- One active run per worktree: `start_playbook` also refuses if the workspace already
  has an active run. A finished run's manager may start a chained playbook in the same
  worktree.
- **When a run ends** (completed, failed or canceled), everything stays: the step agents,
  the manager and the worktree, so conversations remain reachable from the graph. You
  archive the worktree in Paseo when you are done with it, for example once the PR is
  merged.
- **Archiving the worktree** (the `workspace.archived` hook) cancels any active run in it
  and deletes its run files. Nothing else prunes runs.
- The same playbook may run several times at once, each run in its own worktree (two PRs
  in parallel, for example), unless the playbook sets `concurrency: 1` (section 3).

## 3. Playbook YAML (a DAG declared with `needs`)

A playbook is a directed acyclic graph of steps. Each step lists the steps it depends on
in `needs`, the same way GitHub Actions jobs do:

- A step with no `needs` is a root and is ready when the run starts.
- A step becomes ready once every step in its `needs` has completed.
- Steps that are ready at the same time run in parallel.
- The order of steps in the file does not matter.

A step is either an agent step (`role`) or a human gate (`gate`). Loops are the only
backward edges. They are declared explicitly with `on: {<outcome>: {goto: …}}` and are
not part of the DAG.

`defaults/main.yaml` (optional, like an Ansible role's `defaults/main.yml`):

```yaml
agent:
  provider: claude
  model: claude-opus-5-5
  mode: bypassPermissions      # steps run unattended (decision 1); must be allowed by the daemon cap
```

`roles/reviewer/role.yaml`, with its prompt in `roles/reviewer/instructions.md`:

```yaml
title: Reviewer
readonly: true                 # may run alongside other steps (decision 3)
agent:                         # optional; overrides the playbook and defaults/main.yaml
  thinking: high
```

The other roles follow the same pattern. `investigator`, `local_qa` and `babysitter` are
`readonly: true`; `implementer` is not.

`pr.yaml`:

```yaml
title: Pull request
description: Investigate, implement, open a PR and babysit it to a human gate.

agent:                         # optional playbook-wide agent settings
  model: claude-opus-5-5

inputs:                        # the Start form; the manager fills them from a chat request
  request:
    type: string
    required: true
    description: What to change
  base_branch:
    type: string
    default: main

outputs:                       # the run's result
  pr_url: { type: string }     # no value: auto-matched from the step output named pr_url
  pr_number:
    type: number
    value: "{{ steps.implement.outputs.pr_number }}"

next:                          # declared chaining; the manager decides whether to start it
  - playbook: release
    on: completed
    # inputs: { … }            # optional; same-name outputs auto-match

steps:
  - id: investigate
    role: investigator
    inputs: [request]          # list form: every name auto-matched
    outputs:
      plan: { type: string }
    prompt: |
      Request: {{ inputs.request }}

  - id: implement
    role: implementer
    needs: [investigate]
    inputs: [request, plan, base_branch]
    outputs:
      pr_url: { type: string }
      pr_number: { type: number }
      branch: { type: string }
    retries: 1
    timeout: 1h
    prompt: |
      Request: {{ inputs.request }}
      Plan: {{ inputs.plan }}
      Open the PR against {{ inputs.base_branch }}.

  - id: review                 # review and local_qa both need implement,
    role: reviewer             # so they run in parallel
    needs: [implement]
    inputs: [pr_url]
    outputs:
      findings: { type: string }
    prompt: "Review {{ inputs.pr_url }}"

  - id: local_qa
    role: local_qa
    needs: [implement]
    inputs: [branch]
    outputs:
      report: { type: string }
      tests_passed: { type: boolean }
    prompt: "Test branch {{ inputs.branch }}"

  - id: babysit                # join: waits for both
    role: babysitter
    needs: [review, local_qa]
    inputs:                    # map form: explicit sources, or ~ for auto-match
      pr_url: ~
      review: "{{ steps.review.outputs.findings }}"
      qa: "{{ steps.local_qa.outputs.report }}"
    outcomes: [ready, changes_requested]
    agent: { model: claude-sonnet-5-5 }   # step override
    timeout: 2h
    prompt: |
      PR: {{ inputs.pr_url }}
      Review: {{ inputs.review }}
      QA: {{ inputs.qa }}
    on:
      changes_requested: { goto: implement, max_loops: 3 }

  - id: pr_approval
    needs: [babysit]
    gate: The PR is ready. Approve to finish, or reject with a comment to send it back.
    on:
      rejected: { goto: implement }
```

```text
investigate ─▶ implement ─┬─▶ review ───┬─▶ babysit ─▶ ◆ pr_approval ─▶ end
                  ▲       └─▶ local_qa ─┘      │              │
                  └───── changes_requested ────┘              │
                  └───────────────── rejected ─────────────────┘
```

### Fields

| Field                          | Applies to     | Meaning                                                                                  |
| ------------------------------ | -------------- | ---------------------------------------------------------------------------------------- |
| `title`, `description`         | playbook       | Display text. The playbook's ID is its file name (`pr.yaml` → `pr`).        |
| `agent`                        | defaults, playbook, role, step | `provider`, `model`, `mode`, `thinking`, merged field by field. Precedence: step > role > playbook > `defaults/main.yaml` > the manager's own provider and model. The resolved `mode` must be allowed by the daemon cap (section 4b). |
| `instructions.md`              | role           | System prompt for every step that uses the role. Required.                               |
| `title`, `readonly`            | role (`role.yaml`) | `readonly: true` means the role must not edit files. The plugin adds this to its system prompt and checks the checkout after each step. See the concurrency rule and readonly check below. |
| `id`                           | step           | Unique step ID. `end` and `fail` are reserved.                                           |
| `needs`                        | any step       | IDs of the steps that must complete first. Default: `[]` (root).                         |
| `role`                         | agent step     | Role directory name under `roles/`.                                                      |
| `inputs`                       | playbook       | Typed variables (see "Variables"). They make up the Start form, and `start_playbook` takes them. |
| `outputs`                      | playbook       | Typed run results. `value` maps from step outputs; without it, the value is auto-matched by name. Resolved when the run completes. |
| `next`                         | playbook       | Declared chaining: `[{ playbook, on: completed, inputs? }]`. The manager decides whether to start it. |
| `inputs`                       | agent step     | The values the step consumes: a list of names (all auto-matched), or a map of name to a source (`"{{ playbook.inputs.x }}"`, `"{{ steps.<id>.outputs.y }}"`) or `~` (auto-match). |
| `prompt`                       | agent step     | Template rendered by the plugin; it may use only `{{ inputs.<name> }}`, `{{ run.id }}` and `{{ attempt }}`. The manager's brief is appended to it. |
| `outputs`                      | agent step     | Typed values the step must return in `report_step_result`. All are required.             |
| `timeout`                      | agent step     | Optional duration (`30m`, `2h`). `defaults/main.yaml` may set a default; there is none otherwise. |
| `outcomes`                     | agent step     | Allowed outcomes. Default: `[success, failure]`.                                         |
| `retries`                      | agent step     | Extra attempts allowed after `failure`. Default: 0.                                      |
| `concurrency`                  | playbook       | Maximum active runs of this playbook in the Paseo project, across all worktrees, including runs inside it as a sub-playbook (decision 52). Default: unlimited. `1` suits playbooks that touch a shared resource outside the checkout, such as Release deploying to the dev environment. |
| `gate`                         | gate step      | Message shown to the human. Outcomes are `approved` and `rejected`.                      |
| `on.<outcome>`                 | any step       | `complete` (default), `end`, `fail`, or `{ goto: <step id>, max_loops: N }`.             |

### Execution rules

- **Completion:** an agent step's `success`, or the first listed outcome, completes the
  step, and any step whose `needs` are now all completed becomes ready. `failure` retries
  up to `retries`, then fails the run. Any other outcome needs an `on` entry.
- **Gate:** `approved` completes the gate. `rejected` fails the run unless `on.rejected`
  is set.
- **End of run:** the run completes when every step has completed, or when an outcome
  maps to `end`. `fail` fails it at once.
- **`goto`:** resets the target step and every step downstream of it (its descendants
  through `needs`) to pending. The target becomes ready again. In the example,
  `changes_requested` re-runs `implement`, `review`, `local_qa` and `babysit`. A `goto`
  must point to an ancestor of the step that declares it. Steps that are still running
  and are reset have their agents archived.
- **`max_loops`:** counts the times that `goto` has fired. When the limit is reached, the
  plugin raises an automatic "loop limit" gate. Approve allows one more loop; reject fails
  the run.
- **Concurrency rule (shared checkout):** two steps may run at the same time when neither
  is an ancestor of the other. The validator refuses any such pair where both roles can
  edit files, so at most one non-`readonly` step runs at a time.
- **Templates:** plain `{{ var }}` substitution only, with no conditionals or loops.
  Prompts use `{{ inputs.<name> }}`, `{{ run.id }}` and `{{ attempt }}`. Input sources
  and playbook output values use `{{ playbook.inputs.<name> }}` and
  `{{ steps.<id>.outputs.<name> }}` (from the latest completed attempt). Numbers and
  booleans render as text.
- **Timeouts:** when a step's `timeout` expires, the plugin cancels the agent's turn and
  records the attempt as `timeout`. That counts as a failure, so `retries` apply, and the
  manager is woken.
- **Feedback after a loop:** when a step re-runs because of a `goto`, the plugin itself
  adds a "Feedback to address" section to its prompt. That section holds the summary of
  the step, or the comment of the gate, that triggered the `goto`. Templates need no
  conditionals for it.
- **Readonly check:** before a `readonly` step starts, the plugin records the checkout's
  `HEAD` and `git status --porcelain`, and compares them when the step ends. Any change
  fails the attempt with "readonly role modified the checkout". `readonly` is therefore
  enforced, not only written in the prompt. Local QA can still run tests; build output
  in ignored files does not count as a change.
- **Retries:** only `failure` outcomes count against `retries`. An attempt `lost` in a
  daemon restart does not.

### Variables

Inputs and outputs work like Ansible `vars` and `register`, at both playbook and step
level.

- **Types:** `string`, `number`, `boolean`, and `enum` (with `values: [...]`). Each var
  may have `required`, `default` and `description`. There are no objects or lists in v1.
- **Explicit mapping wins:** a step input with a source takes that value.
- **Auto-match by name:** a step input without a source (list form, or `~`) takes the
  same-named, type-compatible output of an **ancestor** step. Failing that, it takes the
  playbook input with that name. Playbook outputs without `value` auto-match from step
  outputs the same way.
- **Ambiguity is an error:** several candidates, or none for a required input, make the
  playbook invalid until the step maps the input explicitly. Nothing is ever chosen
  silently.
- **Checked reports:** `report_step_result` refuses a report that misses a declared
  output or has the wrong type. The error names the output, so the agent fixes it in the
  same turn.
- **Visible wiring:** the detail sheet shows each input's value and source, for example
  `pr_url ← implement (auto)`.
- **Chaining:** a playbook's `next` entries say which playbook can follow and how inputs
  map. Its outputs auto-match the next playbook's inputs by name, as above. When a run
  completes, the manager is told about the available chain and decides whether to call
  `start_playbook`, passing the resolved inputs. Nothing starts automatically. The chained
  run lives in the **same worktree with the same manager**, so it sees the same branch and
  history, and the panel lists both runs. If the next playbook needs another state (for
  example, Release needing the merged main branch), its first step handles it.

Validation runs at load time and errors appear in the Playbooks panel. It checks:

- duplicate IDs
- unknown roles (missing `role.yaml` or `instructions.md`), `needs` or `goto` targets
- cycles in `needs`
- a `goto` that does not point to an ancestor
- `on` keys that are not allowed outcomes
- template references to non-ancestor steps, and prompts using anything other than
  `inputs`, `run` and `attempt`
- unresolved, ambiguous or type-incompatible inputs and outputs
- `next` entries naming an unknown playbook, or leaving a required input unresolved
- pairs of possibly concurrent steps that can both edit files
- a resolved agent `mode` that the daemon cap does not allow

## 4. Run state

One JSON file per run in `$PASEO_HOME/plugin-data/paseo-playbooks/runs/<runId>.json`.
This folder sits next to Paseo's own `plugin-settings/`, outside `$PASEO_HOME/plugins/`,
which Paseo manages: it holds `sources.json` and the checkouts of installed plugins, and
`plugin remove` and `update` delete or replace them. On the lab daemon
that is `/home/paseo/.paseo` on the `paseo-data` volume. Files are written atomically
(temp file, then rename), and writes are serialized per run. Runs therefore survive a
daemon restart and outlive any Hub execution.

```jsonc
{
  "id": "run_7f3k2",
  "playbook": { "name": "pr", "file": ".../.paseo/plugins/playbooks/pr.yaml", "snapshot": { /* parsed */ } },
  "workspaceDir": "/home/paseo/.paseo/worktrees/…/pr-fix-flaky-test",
  "projectId": "proj_...",        // for the playbook's `concurrency` limit
  "workspaceId": "ws_...",
  "managerAgentId": "agent_...",
  "branch": "playbooks/pr-7f3k2",
  "inputs": { "request": "Fix the flaky volume hygiene test", "base_branch": "main" },
  "outputs": null,                // resolved playbook outputs once completed
  "status": "running",            // running | waiting_gate | completed | failed | canceled
  "failure": null,                // e.g. "manager archived", "step implement failed after 2 attempts"
  "createdAt": "...", "updatedAt": "...",
  "steps": {
    "implement": {
      "status": "completed",      // pending | ready | running | reported | completed | failed | waiting
      "loops": 1,
      "attempts": [{
        "n": 1, "agentId": "agent_...", "startedAt": "...", "endedAt": "...",
        "brief": "...",                       // manager's brief
        "inputs": { "request": { "value": "...", "source": "playbook.inputs.request (auto)" } },
        "report": { "outcome": "success", "summary": "...", "outputs": { "pr_url": "..." } },
        "outcome": "success",                 // set by complete_step (the manager may override the report)
        "turnEnd": "completed"                // completed | failed | canceled | lost | timeout
      }]
    }
  },
  "gates": [{ "stepId": "pr_approval", "status": "pending", "message": "...",
              "requestedAt": "...", "decision": null, "comment": null,
              "decidedBy": null, "decidedVia": null }],   // via: panel | chat
  "ready": ["pr_approval"],      // steps the manager may start now
  "inbox": [],                    // wake-ups not yet delivered to the manager
  "history": [{ "seq": 12, "at": "...", "type": "step_completed", "stepId": "implement", "detail": "success" }]
}
```

When the plugin starts, for example after a daemon restart, it reconciles every active
run:
- It rebuilds the agentId → (run, step) index.
- It refreshes each running step agent. One that is no longer running and never reported
  is marked `turnEnd: lost` and queued for the manager.
- It flushes queued wake-ups if the manager is idle.
- **Lost manager:** if a run's manager is archived or ends in an unrecoverable error
  (the `agent.archived` hook, or the reconcile pass finding it gone), the run fails with
  `failure: "manager lost"`. The plugin cancels its running step agents' turns.

## 4b. Daemon-side cap

Playbooks come from the workspace, so any branch can ship one, including an external PR
you check out. A playbook must not be able to give its agents more freedom than the daemon
owner allows. The cap is a plugin settings document (`defineSettings`, `scope: "host"`),
stored by Paseo on the daemon and edited in **Settings → Plugins → paseo-playbooks**, a
small settings screen (`addSettingsScreen`) and not a left-side panel:

```yaml
allowedModes:                 # per provider; resolved step modes must be listed
  claude: [default, acceptEdits]     # default when unset; bypassPermissions is opt-in
```

On the lab daemon, the owner adds `bypassPermissions` to `claude`. A playbook asking for a
mode outside the cap fails validation and cannot start. The repository cannot raise the cap.

## 5. Agent tools

Tools are attached in `before("agent.session_open")`:

- **Manager tools:** every agent whose workspace folder contains
  a playbook file (`.paseo/plugins/playbooks/*.yaml`), except step agents. The workspace lookup is
  cached. This lets an agent that Hub starts become a manager without labels.
- **Step tool:** agents labelled `playbooks/run` and `playbooks/step`. The plugin sets
  these labels when it creates them.
- **Authoring tool:** `validate_playbooks` goes to every non-step agent, even in a
  workspace with no playbooks yet, because the first playbook of a repository is written
  there. It is read-only.

All tools return text for the model plus `structuredContent`. Errors use `isError` with
the reason, for example `transition "implement → pr_approval" is not allowed`.

| Tool                 | Input                                                                    | Effect / output                                                                                                                         |
| -------------------- | ------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| `validate_playbooks` | `path?`                                                                  | Authoring. Loads `<workspace>/.paseo/plugins/playbooks/` (or `path`) with the same loader and validator as the Playbooks panel, including the daemon cap. Returns each playbook as valid or with errors (file, field, message), and the resolved agent settings. Writes nothing. |
| `list_playbooks`     | –                                                                        | Playbooks in this agent's workspace (name, description, steps), any validation errors, and the manager protocol.                         |
| `start_playbook`     | `playbook`, `inputs`                                                     | Creates the run, with this agent as its manager. `inputs` are validated against the playbook's typed inputs; defaults are applied. Refused outside a worktree workspace, when the workspace already has an active run, or when the playbook's `concurrency` limit is reached in the project. Returns `runId` and the first ready steps. |
| `start_step`         | `runId`, `stepId`, `brief`                                               | Refused unless the step is in `ready`, or is a retry within `retries`. Creates the step subagent and returns `agentId` and `attempt`. |
| `complete_step`      | `runId`, `stepId`, `outcome`, `summary?`, `outputs?`                     | Records the outcome and applies the transition. `outputs` may correct the reported values, but they must still match the declared types. Returns the new `ready` steps, a gate to request, `end`, or `fail`. At `end`, it returns the resolved playbook outputs and any `next` chain with its resolved inputs. |
| `request_gate`       | `runId`, `stepId`, `summary`, `details`                                  | Opens the gate (`waiting_gate`). The panel shows the one-sentence summary, with the playbook's gate text and the manager's details collapsed under it. |
| `resume`             | `runId`, `stepId`, `decision` (`approved`/`rejected`), `comment?`, `decidedBy?` | Records a gate decision that arrived by chat. If the panel already decided, it returns that decision. Applies the transition and returns `ready`. |
| `nudge_step`         | `runId`, `stepId`, `message`                                             | Sends a follow-up to the current attempt's agent, in the same context; it does not start a new attempt. Use it when a step ended without reporting, or needs a correction. |
| `get_run`            | `runId?`                                                                 | Run state for the manager. Without `runId`, lists this manager's runs.                                                                  |
| `cancel_run`         | `runId`, `reason`                                                        | Stops the run and archives running step agents.                                                                                         |
| `report_step_result` | `outcome`, `summary`, `outputs`                                          | Step agents only. Validates `outputs` against the step's declared types (all required) and refuses with the missing or wrong names. Stores the report on the current attempt. Called once, as the last action. |

`validate_playbooks`, `list_playbooks`, `nudge_step`, `get_run` and `cancel_run` go beyond the five tools in
the brief. They are small. Without them, the manager cannot discover playbooks, recover
after a restart, or correct a step without losing its context.

The manager calls `complete_step` for every step, including successful ones: reviewing
each result is the manager's job (no auto-accept).

### Paseo's own tools

The manager and the step agents also have Paseo's built-in tools (`create_agent`,
`send_agent_prompt`, and so on). The plugin cannot block them without breaking unrelated
use, so the prompts say:
- the manager creates step agents only with `start_step`
- step agents do not create agents

An agent created outside the plugin is simply not part of the run.

### Step agent creation

The plugin calls `paseo.workspaces.ref(run.workspaceId).agents.create(...)` with:

- `config`: `provider: "<provider>/<model>"`, `modeId`, and `systemPrompt` set to the
  role's instructions plus the step protocol (allowed outcomes, required `outputs`, and
  "call `report_step_result` exactly once, last").
- `parent`: the manager.
- `title`: `"PR · Implementer #2"`.
- `labels`: `playbooks/run`, `playbooks/step`, `playbooks/attempt`.
- `prompt`: the rendered step `prompt`, followed by the manager's `brief`.

### Wake-up protocol

1. `on("agent.turn_ended")` fires for a step agent. The plugin records `turnEnd` and the
   report. Without a report, it records the last assistant message (tail of the timeline).
   The step moves to `reported`.
2. The plugin queues a message in the run's `inbox`, for example:
   `[playbooks] run_7f3k2 · review attempt 1 reported success: "<summary>". outputs: {...}. Ready to complete: review. Waiting on: local_qa.`
3. Delivery to the manager uses `paseo.agents.ref(manager).send(text)`, but only when the
   manager is not in a turn. The plugin tracks this with `agent.turn_started` and
   `agent.turn_ended`. Otherwise the message stays queued and is flushed, merged into one
   prompt, when the manager's turn ends. The plugin never interrupts the manager.
4. A panel gate decision follows the same path:
   `Gate pr_approval approved by Louis via panel: "<comment>".`

## 6. Human gates

- **Panel:** Approve and Reject buttons, with an optional comment, call the `gates.decide`
  RPC. That records `decidedVia: panel`, `decidedBy` set to the Paseo host label, and the
  time, then wakes the manager. The plugin API has no user identity.
- **Notice:** after `request_gate`, the manager ends its turn, so Paseo marks it as
  needing attention and sends its usual notification (a push on mobile). The gate node
  turns amber. There is no extra mechanism.
- **Slack (later, with Hub):** the manager posts the gate message with `hub.reply`. A reply
  such as `@bot approve` reaches the same agent through Hub conversation continuation. The
  manager then calls `resume(..., decision, decidedBy: <Slack user ID>)`.
- Whichever decision arrives first wins. A second decision gets back the first.

## 7. UI

The plugin has **one** workspace panel, **Playbooks**, in Explorer, Paseo's right-hand
sidebar (`addWorkspacePanel`, `locations: ["explorer"]`). There is no left-side screen,
because playbooks are per workspace. A playbook at rest and a running one share a view:
the run draws the same step graph, with live status added.

The panel uses React Native primitives only (`View`, `Text`, `Pressable`, `ScrollView`,
and `TextInput`). Colors come from `theme.colors` and spacing from `layout.compact`, so it
works on mobile. Paseo 0.14.0 has no plugin subscriptions, so the panel polls through
TanStack Query: every 3 s while a run is active, every 30 s otherwise, and on ⟳.

### Contents

- **One card per playbook** in this workspace's `.paseo/plugins/playbooks/`. Each card
  has the title, file, and any validation errors. A card with errors cannot start a run.
- **The step graph:** drawn as a graph (see "Graph rendering" below), with each step's
  role (`ro` marks readonly roles), its `needs` edges, and its `goto` loops. Roles and their
  resolved agent settings and instructions are in a collapsible section.
- **Runs:** the panel lists only the runs **in this workspace**. Each run has its own
  worktree, so the panel shows at most one active run, plus earlier finished ones. In the
  main checkout it shows definitions only.
- **Run overlay:** when a run of a playbook is in this workspace, the same graph shows
  the run's state on every node: status, attempt and loop counts, and the agent's live
  status (`useAgent`). "Needs permission" shows when a step agent waits on a permission.
  A run selector switches between the active run, finished runs, and the bare
  definition.
- **Pressing a node** opens the conversation of its latest attempt
  (`navigation.openAgent`). Attempt chips (`#1 #2`) on the node open earlier attempts.
  An ⓘ on the node opens a detail sheet (`Modal` from `@getpaseo/plugin/client/ui`, a
  bottom sheet on mobile) with:
  - status, timings, the manager's brief, each input with its value and source
    (`pr_url ← implement (auto)`), and the report summary and outputs
  - every attempt, each opening its conversation
  - for a gate: the message, a comment field, and Approve and Reject. A pending gate also
    shows its Approve and Reject directly under its node.
- **Start** (on each valid card) opens a form built from the playbook's typed `inputs`:
  a text field for `string`, a numeric field for `number`, a switch for `boolean`, and a
  picker for `enum`, with defaults and descriptions. It then creates a worktree
  workspace, starts a manager agent there with the manager protocol prompt, and opens
  that workspace (`navigation.openWorkspace`). Start is refused with the reason when the
  playbook's `concurrency` limit is reached. It warns, without blocking, when an active
  run of the same playbook in the project has the same request. This is the way to start
  a run inside Paseo while Hub is parked.
- **Run outputs:** a completed run shows its playbook outputs on the card (`pr_url` as a
  link), and any `next` chain the manager was offered.
- **Run controls:**
  - **Cancel run**, with confirmation: cancels running step agents' turns, marks the run
    canceled, and tells the manager.
  - **Retry step**, on a failed node: sends the manager a wake-up asking it to retry. The
    manager still writes the brief.
  - **Nudge step**, on a running or reported node: a text field that sends a follow-up to
    the step agent, the same as the manager's `nudge_step`.

### Graph rendering

Plugins cannot import `react-native-svg`, so the graph uses only React Native views. It is
laid out from top to bottom, which suits the narrow Explorer sidebar and phones:

- **Layers:** a step sits one layer below the deepest step in its `needs`. Steps on the
  same layer sit side by side and scroll horizontally if a layer is wider than the panel.
- **Edges:** 1-pixel `View` lines in `theme.colors.border`, laid out like an org chart. A
  horizontal connector line forks a step into a layer and joins it back
  (`implement` → `review` and `local_qa` → `babysit`).
- **Loops:** `goto` edges point back up the graph, so they are not drawn as lines. They
  appear as a "↺ implement · 1/3" badge on the step that loops. Pressing the badge
  highlights the target node.
- **Nodes:** rounded cards built from `theme.colors.surface1`, with the step ID, role
  title, and icons from `Icon`. Gates are drawn as a diamond-marked card.
- **States:**
  - running: an accent border (`theme.colors.accent`) with a gentle pulse from React
    Native's `Animated`; the pulse stops under the OS "reduce motion" setting
  - completed: a `statusSuccess` check
  - failed: `statusDanger`
  - waiting at a gate or needing permission: `statusWarning`
  - steps the run has not reached yet: dimmed
  - the edges into the running node are highlighted as well
- **Accessibility:** each node is a `Pressable` with `accessibilityRole="button"` and a
  label, for example "review, Reviewer, running, attempt 2, opens conversation".

## 10. Decisions

1. **Step agent permissions:** the example playbook uses `bypassPermissions`, so steps run
   unattended. Playbooks can override the mode per role, within the daemon cap
   (decision 15), and the panel still flags any step agent waiting on a permission.
2. **Who becomes a manager:** any non-step agent whose workspace folder has
   a playbook file in `.paseo/plugins/playbooks/` gets the manager tools. No label is needed, so Hub-started
   agents qualify.
3. **Shared checkout:** steps that can run concurrently (neither is an ancestor of the
   other) must not both be able to edit files. The validator enforces this with the role
   flag `readonly: true`.
4. **Loop limit:** reaching `max_loops` opens an automatic "loop limit reached" gate.
   Approve allows one more loop; reject fails the run.
5. **Playbook location:** the workspace folder (`<workspace>/.paseo/plugins/playbooks/`),
   not the project root and not the plugin repository.
6. **UI:** one panel on the right, Playbooks. It shows each playbook's step graph and,
   for a run in this workspace, the same graph with live status, agents and gates. No
   left-side screen.
7. **Lab install:** from the Git source, after asking first.
8. **Hub trigger:** parked.
9. **Graph:** steps form a DAG through `needs`, replacing `parallel` blocks. Loops are
   explicit `goto` back-edges that reset the target and its descendants.
10. **Conditional branches:** not yet. Each outcome either completes the step, loops with
    `goto`, or ends or fails the run. Outcome-qualified `needs` or `when:` can be added
    once a playbook such as Release needs them.
11. **Repository layout:** `.paseo/plugins/playbooks/` holds the playbooks as top-level
    `<id>.yaml` files, as in Ansible, plus `defaults/main.yaml` and
    `roles/<id>/{role.yaml,instructions.md}`. Roles are shared across playbooks.
12. **Agent precedence:** step > role > playbook > `defaults/main.yaml` > the manager's own
    provider and model, merged field by field.
13. **Run state location:** `$PASEO_HOME/plugin-data/paseo-playbooks/runs/`, outside the
    `$PASEO_HOME/plugins/` folder that Paseo manages.
14. **Worktree per run:** every run lives in its own Paseo worktree workspace, created by
    Start. `start_playbook` refuses outside a worktree, and when the worktree already has
    an active run.
15. **Daemon-side cap:** plugin settings on the daemon list the allowed modes per
    provider; `bypassPermissions` is opt-in. `readonly` is enforced by comparing the
    checkout before and after each readonly step, instead of using Claude's `plan` mode,
    which would block Local QA's commands.
16. **Templates:** plain `{{ var }}` substitution. The plugin adds the "Feedback to
    address" section after a `goto`.
17. **`nudge_step`:** sends a follow-up to a step agent within the same attempt. Attempts
    lost in a daemon restart do not count against `retries`.
18. **Manager review:** the manager calls `complete_step` for every step (no auto-accept).
19. **Timeline rows:** dropped from v1.
20. **Authoring:** the repository ships `skills/paseo-playbooks/SKILL.md`, which
    repositories opt into by copying or symlinking it. The plugin never writes skills.
    The plugin adds a read-only `validate_playbooks` tool to every non-step agent,
    backed by the same validator as the Playbooks panel.
21. **Run scope in the panel:** the panel lists only the runs in the current workspace
    (at most one active run, because each run has its own worktree).
22. **Concurrency:** the same playbook may run in parallel in separate worktrees. A
    playbook can set `concurrency: 1` (or N) to limit active runs across the project. Start
    warns, without blocking, when an active run has the same request.
23. **Graph view:** a top-down layered graph built from React Native views. Edges are
    org-chart-style connector lines. `goto` loops are badges on their nodes. The running
    node pulses with an accent border (no pulse under "reduce motion"), and other states
    use theme status colours.
24. **Node press:** opens the latest attempt's conversation; attempt chips open earlier
    ones. An ⓘ opens a detail sheet (brief, report, outputs, attempts, gate actions).
25. **Branch:** the worktree branch is the PR branch, `playbooks/<playbook>-<runId>`.
26. **Manager settings:** an optional `manager:` block in `defaults/main.yaml`, falling
    back to the `agent` defaults, then to Claude Opus in `default` mode.
27. **Run end:** everything is kept (step agents, manager, worktree).
28. **Timeouts:** an optional `timeout` per step, with an optional default in
    `defaults/main.yaml`. Expiry counts as a failure.
29. **Panel controls:** Cancel run, Retry step (through the manager), and Nudge step,
    plus gate Approve and Reject.
30. **Paseo's own tools:** the prompts tell agents not to use them; nothing blocks them.
31. **Test target:** the workstation daemon, with the plugin installed from this
    directory.
32. **Retention:** run files are deleted when their worktree workspace is archived.
33. **Variables:** typed `inputs` and `outputs` (`string`, `number`, `boolean`, `enum`)
    on playbooks and steps. Prompts use only `{{ inputs.x }}`. An explicit mapping wins;
    otherwise inputs auto-match by name from ancestor outputs, then playbook inputs.
    Ambiguity is a validation error. Step outputs are required and type-checked when the
    step reports.
34. **Chaining:** `next:` on a playbook, with same-name auto-matching of outputs to the
    next playbook's inputs. The manager decides whether to start the next playbook.
35. **Lost manager:** the run fails and its running steps are cancelled.
36. **Gate actor:** a decision records the channel (`panel` or `chat`), the Paseo host
    label or the Slack user ID, and the time.
37. **Chained runs:** they live in the same worktree, with the same manager.
38. **Paseo compatibility:** `>=0.14.0 <0.15.0`.
39. **Gate notice:** Paseo's own attention notification when the manager ends its turn.
40. **Second folder:** playbooks are also loaded from `.paseo/playbooks/`. Both folders are
    merged; each is self-contained (its own `roles/` and `defaults/main.yaml`), and the
    same playbook id in both is a validation error on both entries.
41. **Start with the workspace's agent (supersedes 14 and 21 in part):** Start is a split
    button. **Start** runs the playbook with the current agent: the most recent agent of
    the workspace that manages no active run (the panel cannot see which tab has focus).
    The run happens in this workspace, on its current branch. The plugin creates the run,
    reloads the agent so that `session_open` gives it the manager tools, and sends it the
    kickoff. A busy agent is never interrupted: the run is created at once and the kickoff
    is sent when its current turn ends (kept in memory, so lost if the daemon restarts first). The chevron menu has one entry for now, **Start on a
    new agent**, which keeps decision 14: a new worktree and a new manager. `start_playbook`
    works in any workspace; the rule is one active run per workspace.
42. **Gate text:** `request_gate` takes a one-sentence `summary` and longer `details`. The
    panel shows the summary on the gate and keeps the details (the playbook's `gate:` text,
    then the manager's details) in a collapsed section. Loop-limit gates split the same way.
43. **Gate choices:** a gate's buttons are declared in YAML under `choices` (outcome → `label`,
    `comment: none | optional | required`), in order; the default is Approve / Reject. Where a
    choice leads still comes from `on` (first choice completes, others fail by default). The
    panel stacks one full-width button per choice with its destination; a choice that takes a
    comment opens a text box with Send. The engine refuses unknown choices and a missing
    required comment.
44. **Choice colours:** a choice may set `color` to a theme colour name (`primary`,
    `neutral`, `success`, `warning`, `danger`), never a hex value, so buttons follow the Paseo
    theme. Default: primary for the first choice, neutral for the others; the default Reject
    and the loop-limit "Stop and fail the run" are danger.
45. **Unknown YAML keys are ignored:** playbook, step, role, choice and defaults files accept
    keys the plugin does not know, and drop them. Known keys are still validated (types,
    values, references), so a typo in a known key's value is still an error.
46. **Archive a run:** the run tab's menu offers "Archive run" for finished runs (completed,
    failed or canceled). It sets `archivedAt` and hides the run from the panel; the run file,
    its history and every agent it used (manager and steps) are kept. Active runs must be
    canceled first. The other way round is automatic: archiving the manager agent archives
    all its runs (an active one is failed first, "manager lost").
47. **No mode cap (supersedes 15):** playbooks may use any agent mode, `bypassPermissions`
    included; the "Allowed agent modes" settings screen and its validation are removed. The
    daemon owner accepts that a repository's playbooks can run steps that execute shell
    commands unattended, and only starts playbooks from repositories they trust. `readonly`
    roles are still enforced by the checkout check.
48. **Three ways to start:** Start (the workspace's current agent manages the run), "Start on
    a new agent" (a new Playbook Manager agent in the same workspace, on its current branch;
    the run id is reserved for it like for a new worktree) and "Start in a new workspace"
    (decision 14: a new worktree on a new branch and a new manager). One active run per
    workspace still applies to the first two.
49. **Sub-playbooks:** a step may be `playbook: <id>`, another playbook of the same folder.
    The loader expands it into the parent (ids prefixed `<step>.`), so it is one run, one
    manager and one graph; the engine, tools and run rules are unchanged. The block's
    inputs are the sub-playbook's inputs (auto-matched or mapped), its outputs the
    sub-playbook's outputs; its first steps take its `needs`, and steps that need it wait for
    its last steps. Nested blocks work; a playbook that includes itself is an error.
50. **Goto to a block** restarts the whole block from its first step, with the feedback
    (the sub-playbook must have exactly one first step). Loops inside a block stay inside.
51. **Display:** steps of a block are shown by their own name ("Investigate"); the panel
    draws a labelled frame around each block. `outputs` joins `end` and `fail` as a reserved
    step id, since sub-playbook ids contain dots.
52. **Concurrency of a sub-playbook:** `concurrency` on a playbook also applies where it runs
    as a sub-playbook, instead of being ignored. The slots are shared by every run of the
    Paseo project, and top-level runs of that playbook count too (decision 22 is unchanged for
    them). A block holds a slot from when its first steps leave `pending`/`queued` until all its
    steps complete or the run ends. The loader keeps the limit on the block (`blocks[prefix].
    concurrency`). When the first steps of a limited block would become `ready` and the block is
    not held, the engine marks them `queued` (new step status, `queuedAt` orders the queue)
    instead. After every change that can free a slot (a step completes, a gate is decided, a run
    is canceled, failed or deleted, a restart) the runtime admits queued blocks oldest first
    while slots are free, turns their steps `ready` and wakes their manager. The panel shows
    queued steps as "waiting for a free slot". The engine stays pure: admission is a function
    of all runs (`shared/slots.ts`), applied by the runtime. A goto that resets the block's
    first steps gives the slot back and queues again. The alternative, a named `lock:` on a
    step or block, was not needed: it would add a second concept for the same effect.
