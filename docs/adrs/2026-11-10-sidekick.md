# Sidekick: a coordinator agent for the playbooks

Status: Accepted

## Context

Watching the runs, deciding what reaches a human and improving the playbooks so it reaches them less is
work that belongs to no single run. Today it lands on whatever agent the user happens to open. The plugin
API cannot host a workspace-free agent (an agent always lives in a workspace, and the SDK gives a plugin
no model access of its own), and it exports no embeddable agent view: a plugin screen cannot draw the
native chat. It can, however, create a workspace flagged `background` (hidden from the
sidebar) and ask the app to open any agent with `navigation.openAgent`.

## Decision

- One Sidekick per host: a real Paseo agent in a hidden background workspace (the host removed public `internal` workspaces: only `background`), a plain empty directory
  `sidekick/` under the plugin data. It is created on first use by the RPC `sidekick.open` and recreated
  (same workspace) if the agent was archived. Its ids are kept in `sidekick.json` next to the runs.
- The Playbooks screen has a Sidekick button that calls `sidekick.open`, then `navigation.openAgent`. The
  host's native agent UI is the chat: no chat code in the plugin, and where it docks is the host's call.
- It is a coordinator, never a worker. Claude's `Bash`, `Edit`, `Write` and `NotebookEdit` are
  disallowed in its config; its prompt makes it hand every job that touches files to a subagent it creates
  with Paseo's `create_agent` in the right project's workspace. It is given the plugin's read tools for runs, gates and
  events, `validate_playbooks`, `cancel_run` and `restart_run`, plus Paseo's agent and workspace tools,
  pre-approved. Playbook changes go through a subagent: new branch off fresh default branch,
  `validate_playbooks`, a pull request that the human merges.
- The plugin subscribes it to `gate.escalated`, `run.failed` and `run.manager_lost` (delivery `idle`) when it
  creates it. It judges each decision that reaches the human ("automatable" or "should stay human") and
  proposes the rule or playbook change that removes it. It never decides a sensitive gate (security, auth,
  secrets, billing, data loss, production data).
- The prompt (`server/sidekick.ts`) is generic: no organisation, ticket system or release process. Model and
  provider are the managers' defaults, changeable in the native UI. No playbook format change.

## Consequences

- The Sidekick agent has no `playbooks/manager` label and its workspace has no playbooks, so it gets only
  the common tools, not a manager's.
- Disallowing tools is enforced for the Claude provider only; on other providers the prompt is the limit.
- Archiving the hidden workspace by hand loses the Sidekick's history; the next open makes a new one.
- A later change could expose a `sidekick` block in `defaults/main.yaml` (provider, model, mode) if a
  per-repository setting is wanted; the Sidekick is host-wide today.
