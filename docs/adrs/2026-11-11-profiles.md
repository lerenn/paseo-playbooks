# Profiles: opt-in playbook repositories next to the default one

Status: Accepted

## Context

Users want personal or specialised collections of playbooks, roles and defaults without
editing the shared catalog. The playbooks folder is already a self-contained repository:
playbook files at its root, with their own `roles/`, `defaults/` and `scripts/`. The loader
reads two such folders (`.paseo/plugins/playbooks/` and the older `.paseo/playbooks/`).
There is no singular `.paseo/plugins/playbook/` folder in the code, and playbook files do not
live in a `playbooks/` subfolder, so neither needed a migration.

## Decision

- **A profile is a repository with the same layout as the playbooks folder.** Each direct
  subfolder of `.paseo/plugins/playbooks/profiles/` is a profile; its name is the profile id
  (lowercase letters, digits, `-`, `_`; `default` is reserved). Nested folders are not
  scanned. Folders that are not valid profile ids are ignored with a diagnostic. No new schema.
- **Default repository.** The existing playbooks folders (`.paseo/plugins/playbooks/`, plus
  the legacy `.paseo/playbooks/`, read as before) are the `default` repository: always
  active, never listed in the config. The legacy folder stays read-only input; nothing is
  moved or deleted, and a diagnostic notes it. Users who never use profiles see no change.
- **Activation is a user-level choice.** `profiles.active` (a list of ids) in
  `$PASEO_HOME/plugin-data/paseo-playbooks/config.yaml`, global to all workspaces, nothing
  stored in the profile folders. All profiles are off by default. Unknown, non-string or
  `default` entries are ignored. A new RPC `playbooks.set-profile` edits the list; the
  loader reads the config on every load, so no restart is needed.
- **Catalog = default + active profiles.** Each repository loads with its own roles,
  defaults and scripts, so a playbook only resolves resources (roles, sub-playbooks,
  hand-offs) inside its own repository.
- **Qualified ids.** A default playbook keeps its bare id (`deploy`), so existing runs and
  references stay valid; a profile playbook is `profile:id` (`louis:deploy`), in
  `PlaybookEntry.id`, `Playbook.id` and run state. `default:deploy` also names the default
  one. Entries carry `repo`.
- **Collisions.** The same bare id in two repositories keeps both resources. A diagnostic
  warns. A bare reference to a shared id (from `start_playbook` or any user-facing lookup)
  is an error that lists the qualified ids; a qualified one always works. Internal lookups
  (the panel, restarts, hand-offs) use the exact id. The same id in the two default folders
  stays an error, as before.
- **UI.** The Playbooks panel shows "Default, always active" and a checkbox per discovered
  profile (shown only when profiles exist), with layout diagnostics. Cards of a profile show
  their repository.
- The execution engine is unchanged: it receives resolved playbooks.

## Consequences

- Profiles are optional and cost nothing when absent.
- A workspace with only profiles still shows the panel, so they can be turned on.
- The activation choice follows the user, not the repository, and is the same in every
  workspace.
- `LoadResult` gains `profiles` and `diagnostics`; the `playbooks.list` RPC output gains the
  same, with defaults, so older clients keep working.
