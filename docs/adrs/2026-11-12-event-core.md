# Event core: run state as the result of an append-only event log

## Status

Accepted

## Context

Louis decided that an event system is the core of the plugin, after an assessment that recommended the incremental option. Today:

- A run is one JSON file, rewritten whole on every mutation (`RunStore.mutate` clones the run, runs a callback, writes the file). The biggest real run file is 3.8 MB with 1172 history entries; rewriting it costs 8-15 ms (measured below), for every mutation, including a one-line change.
- Every state change is an imperative mutator (about 81 exported in `engine.ts`, about 79 `store.mutate` sites in `runtime.ts`). The facts they change are recorded a second time, as free text, in `run.history` (`log()`, about 52 sites). The history is append-only with a per-run `seq`, but its entries are prose (`detail`), not data.
- The event bus (`bus.ts`) is a read-side projection: `OversightProducer.scan` reads `run.history` with in-memory cursors and emits bus events. The bus keeps 500 events (about 1.6 h) and is rewritten whole on every emit. It cannot be the log.
- Three wake-up mechanisms exist side by side: the `tick()` loop, the script steps' `setTimeout` polls, and the bus (agents only). See `2026-11-12-event-core-internal-wakeups.md`.

The assessment's warnings stand and shape how this is done: no big-bang rewrite; the public tool API, `subscribe_events` / `list_events`, `restart_run`, manager modes `always_on` / `none`, existing playbooks and existing run files must keep working; external systems (code hosts, trackers, deploy branches) are only observed, never by events; a major version only with an ADR. The migration is in `2026-11-12-event-core-migration.md`.

## Decision

1. **Commands, events, reducers.** A command (a tool call, a tick, a hook, a script result) is validated against the current state and, if allowed, produces events. An event is a fact in the past tense (`job.boarded`). A reducer is a pure, deterministic function `(run, event) -> run` that uses only the event's data. The run state is what the reducers make of the events. Nothing else may change event-sourced state.
2. **Areas.** Migration is per area: a slice of run state with its own events and reducers (`Area` in `server/event-core.ts`; first area: `jobs`, the pipeline's jobs and stations). A run may have some areas event-sourced and others not. An event type belongs to exactly one area.
3. **Streams.** One stream per run, identified by the run id. Order is total inside a stream (`seq`: 1, 2, 3, never reused). There is no order across streams: a fact that matters to two runs (a train's job settled in the pipeline and mirrored on the train) is two events, one per stream, each recorded by the mutation that changed that run. Cross-run order for readers is the bus's `seq`.
4. **Envelope.** One JSON object per line: `{ v, stream, seq, type, at, data }`. `v` is the envelope version (1). `type` is `<area>.<fact>`. `data` holds results, not deltas ("outputs after", not "outputs to merge"), so a reducer is an assignment, and an event needs no knowledge of the state before it. History lines (`run.history`) are derived by the reducer from the event's data, with the same text the mutators write today, so history stays readable and later becomes derivable.
5. **Genesis.** A stream is not required to start empty. Each area starts at an `<area>.genesis` event whose `data.state` is the area's state at that moment. A run that existed before the log gets its genesis lazily, at the first event of the area, from the snapshot. The latest genesis of an area is the point replay starts from. This is also how a log is re-baselined (below) and compacted.
6. **Snapshot.** The run JSON stays, as a cache of the reducers' result and, until stage 6 of the migration, as the source of truth. It records `eventSeq`: the last log entry it includes (default 0, so old files load unchanged). Order of writes in a mutation: append events to the log, then write the snapshot. A crash between the two leaves `log.lastSeq > eventSeq` (events that never took effect: re-baseline). A failed or missing log write leaves `log.lastSeq < eventSeq` (same: re-baseline). Re-baselining is a new genesis per area from the snapshot; old lines stay in the file, superseded.
7. **Idempotency and restart.** Seq is assigned at append, by the store, per stream, after the head read from the file. Replay always starts from a genesis and applies each line once, in order; a reducer applied twice to the same event leaves what it assigned (it is not idempotent for event types that add something, e.g. `job.queued`, and does not have to be: the seq, not the reducer, protects against replay twice). On start, with parity on, every log is rebuilt from its latest genesis and compared with its snapshot; a mismatch is reported, not repaired.
8. **Persistence format and location.** `runs/<run id>.events.jsonl`, beside `runs/<run id>.json`, one file per stream. Per run, not per pipeline: the snapshot is per run; deleting a run deletes its log and nothing else; a train's mirrored events and a pipeline's job events do not share a file, so there is no writer shared between two per-run queues. An append is one `write` of whole lines to a file opened in append mode, inside the run's existing mutation queue, so appends of a stream never interleave. A crash leaves complete lines plus at most one torn last line; reading drops it and opening the stream cuts it off before the next append. A damaged middle line or one with an unknown envelope version is skipped and counted (never guessed). The `.events.jsonl` suffix does not end in `.json`, so older plugin versions' loader ignores the files.
9. **Compaction.** A stream above 1 MiB (default) is rewritten at its next append as one genesis event per area at the current state (temp file, then rename), seq continuing. Disk growth is bounded by that size plus the events since; a deleted run deletes its log. Full history of a run stays in `run.history`, not in the log. Whether the log should keep a longer tail for audit is open (see Consequences).
10. **Schema evolution.** An event type's `data` may only grow optional fields in the same `v`. A breaking change of a type is a new type name (`job.boarded.v2` is not used: pick a new fact name). A change of the envelope bumps `v`; a reader skips lines of a `v` it does not know, so a downgrade ignores what it cannot read and re-baselines (rule 6).
11. **Validation.** Commands validate before they record: the engine mutators keep their guards (`EngineError`). An event is only recorded after its guards passed. Reducers never validate and never throw for a valid log; an unknown event type is an error found by parity, not applied.
12. **External world.** Code hosts, trackers, deploy branches and the like are never events. The truth about them is a state check (a script that asks). A state check may produce an event (`job.held`, `job.admitted`) because it is the plugin's own decision, taken on the observed state. An event may be used as a hint, "look again now" (`wake_on`), never as the answer.
13. **Public events.** Some domain events become public bus events (`job.*`), mapped from the committed event, not derived later from history. The bus stays a capacity-bounded read-side store for agents (`list_events`); the log is not exposed. See `2026-11-12-event-core-job-events.md`.

## Consequences

- One recording of each fact, as data: state, history text, public event and later wake-ups come from the same event.
- Per-mutation cost moves from a whole-file rewrite (8-15 ms for the biggest run) to a 200-byte append (0.03 ms) once the snapshot is no longer written per mutation; until stage 6 both are paid, plus one `structuredClone` for the parity check (about 3 ms on the biggest file) on mutations that record events. The snapshot may later be written lazily (every N events or on a timer, from the reducers' result), with `eventSeq` telling what it includes; that is a separate decision.
- Risks, stated plainly. (a) Two models in the code for a while: every migrated mutator is written twice (mutator and reducer) until stage 6, and the tests of that area double. (b) A reducer that diverges from its mutator is only found if a test or a real run exercises the path; the parity check covers every mutation that records events, but only on the paths the events describe. (c) Ordering across runs is not defined by the log. (d) A downgrade after upgrade loses nothing in the snapshot, but the log goes stale and is re-baselined. (e) Compaction drops event history older than the latest genesis; that is acceptable only while the snapshot is the truth. (f) Events carry whole `outputs` and job inputs: log lines of a pipeline with large outputs grow; compaction bounds them.
- Not determined: how many mutations per second a busy pipeline makes in practice (only the history length, 1172 entries for the largest run, is known); whether a run that is both pipeline and train-heavy needs a log per area; whether users want a longer audit tail than compaction leaves.
