# Warden: one periodic, opt-in pass over the active runs

## Status

Accepted

## Context

Several watchers already exist, each with its own rule and event: the manager watchdog (`manager.nudge`, ADR
2026-11-18-manager-waiting-watchdog: `step.waiting_manager_stuck`, `manager.question_pending`), the slow-step warning
(`slow_warning`, `step.slow`), the stale gate event (`gate.stale`) and the stale-session sweeps. None of them tells a human
that a run is pinned to an older definition than `origin/<base>` (the definition is pinned at the run's start), that a
goto edge looped many times, or that a manager is gone or idle while a gate only it can decide waits. Each fires on its
own schedule, with no common switch, cooldown or summary.

## Decision

- A `warden` block, in `defaults/main.yaml` (repo-wide) and in a playbook (field by field override, like `slow_warning`), resolved
  into the run's playbook at its start (like `manager.nudge`):
  `warden: { enabled: false, interval: 15m, cooldown: 1h, checks: { stale_definition: { action: report }, manager_blocked: { action: report }, loops: { above: 5, action: report }, slow: { action: report }, gate_open: { after: 30m, action: report } } }`.
  **It is OFF by default**: `enabled` defaults to false in the schema, the loader and the shipped defaults. With no block, or
  `enabled: false`, nothing runs: no scan, git or agent read, event, panel notice or Sidekick message (tested). Unknown keys fail
  validation; `action` is `report | none` (`none` turns that check off), and `refresh_scripts` is also allowed on `stale_definition`.
- One pass from the existing event scan (no new timer), looked at most every 30 s; a run is looked at once per `interval`, at most
  25 runs per pass (the longest-waiting first), async I/O only, each check and each run in its own try/catch.
  It makes no LLM call and sends no nudge or prompt to a run's agents.
- Checks and what they reuse:
  - `stale_definition` (new event `warden.finding`): `run.definition` is `workspace` or its `sha` differs from `origin/<base>` after a fetch.
    Only runs with a worktree. Action `refresh_scripts` calls the existing `Runtime.refreshScripts` (so, on an active run, scripts are
    refreshed and the definition stays pinned, as that tool says), once per finding.
  - `manager_blocked` (new event `warden.finding`): the manager is gone (archived, closed, errored) with any gate open, or idle with a
    gate only it holds (`gateHolder`, the same holder rule as the watchdog's `blockedOnGate`). A gate held by a human is not a finding while the manager is alive.
  - `loops` (new event `warden.finding`): `run.loops[edge] > above`.
  - `slow`: the existing `SlowIndex`; **no new event**, `step.slow` already announces it.
  - `gate_open`: the age `gateListing` computes for `gate.stale`; **no new event**, `gate.stale` already announces it.
  So a finding of `slow` or `gate_open` reaches the panel, `get_run` and the Sidekick summary, never a second event.
- Findings are kept in the run (`warden.findings`, defaulted, so older run files load; survives a restart). A finding is keyed by check and
  subject; it is reported once (event, summary), not again while unchanged, again after `cooldown` if still true, forgotten when it clears
  and reported anew if it comes back, and a changed signature (a new origin sha, a new step run) is a new finding. The state is written before any effect.
- Surfaces: `warden.finding` in `list_events` and `subscribe_events` (scoped, not in the Sidekick's default `watch`); an additive, optional
  `warden` list in `get_run`; a one-line warning per finding in the run's panel header. If the project's Sidekick agent runs, it gets ONE
  message per pass with only the new or changed findings, sent when it is idle (held until its turn ends otherwise, like the other
  notices); without a Sidekick nothing is sent. No new tool: `get_run` and `list_events` suffice.

## Consequences

- A team can opt in and get one deduplicated stream of "this run needs a look", with per-check control, without a second copy of the
  slow, gate and manager logic.
- A pass costs one `git fetch` per distinct base and one agent read per distinct manager, bounded by the cap and `interval`.
- The configuration is frozen into a run when it starts (like every playbook field): turning the warden on affects runs started afterwards.
- It overlaps with `step.slow`, `gate.stale` and the watchdog by design for `slow` and `gate_open`; set the warden check to `action: none` to see only the originals.
- The stale-sessions sweeps are unrelated (sessions, not runs) and untouched.
