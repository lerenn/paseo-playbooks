Examples

Five complete playbooks: Pull request, Release to dev, Route a change and Capability are in examples/, and Docs check is at the root of this repository. Copy a folder into your repository as .paseo/plugins/playbooks/ or .paseo/playbooks/, adjust it, then run validate_playbooks.

  • Pull request: investigate runs first, then implement, then review and local QA run in parallel, and babysit the PR until it is green.
  • Capability: the Pull request playbook, a human gate, then the Release to dev playbook, as sub-playbooks.
  • Release to dev: deploy the change to the development environment, check it there, and redeploy when the check asks for it.
  • Route a change: classify a change, then take the branch that fits it (if / else-if / else on a step's output), and join.
  • Unattended change: a run with no Playbook Manager: the plugin drives it, a human gate and a role gate decide.
  • Docs check: compare the docs with the code, fix them, review and check in parallel, loop until clean, human gate. It needs no shell commands.

Pull request

From examples/.paseo/plugins/playbooks/. Steps run with bypassPermissions, so they run shell commands without asking. The Implementer pushes and opens the PR with gh.

investigate ─▶ implement ─┬─▶ review ───┬─▶ babysit ─▶ end
                  ▲       └─▶ local_qa ─┘      │
                  └───── changes_requested ────┘

pr.yaml

title: Pull request
description: Investigate a request, implement it, open a PR and babysit it until it is green.
manager:
  prompt: Before you accept the implement step, check that its PR exists and targets the base branch.

inputs:
  request:
    type: string
    required: true
    description: What to change
  base_branch:
    type: string
    default: main
    description: Branch the PR targets

outputs:
  pr_url: { type: string }     # auto-matched from the implement step
  pr_number:
    type: number
    value: "{{ steps.implement.outputs.pr_number }}"

steps:
  - id: investigate
    role:
      name: investigator
      prompt: |
        Request: {{ inputs.request }}
    inputs: [request]
    outputs:
      plan: { type: string, description: Implementation plan }

  - id: implement
    role:
      name: implementer
      prompt: |
        Request: {{ inputs.request }}

        Plan:
        {{ inputs.plan }}

        Open (or update) the pull request against {{ inputs.base_branch }}.
    needs: [investigate]
    inputs: [request, plan, base_branch]
    outputs:
      pr_url: { type: string }
      pr_number: { type: number }
      branch: { type: string }
    retries: 1
    timeout: 1h

  - id: review
    role: { name: reviewer, prompt: "Review the pull request {{ inputs.pr_url }}." }
    needs: [implement]
    inputs: [pr_url]
    outputs:
      findings: { type: string }

  - id: local_qa
    role: { name: local_qa, prompt: "Test the branch {{ inputs.branch }}." }
    needs: [implement]
    inputs: [branch]
    outputs:
      report: { type: string }
      tests_passed: { type: boolean }

  - id: babysit
    role:
      name: babysitter
      prompt: |
        Pull request: {{ inputs.pr_url }}

        Review findings:
        {{ inputs.review }}

        Local QA report:
        {{ inputs.qa }}
    needs: [review, local_qa]
    inputs:
      pr_url: ~
      review: "{{ steps.review.outputs.findings }}"
      qa: "{{ steps.local_qa.outputs.report }}"
    outcomes: [ready, changes_requested]
    timeout: 2h
    on:
      changes_requested: { goto: implement, max_loops: 3, decider: { by: role, role: gatekeeper } }

defaults/main.yaml

# Repo-wide agent defaults. Precedence: step > role > playbook > these > the manager's own.
# Switching provider is one edit here: change the tiers, every `agent: { tier: … }` follows.
tiers:
  cheap:                       # a list: when claude is out of tokens, the step moves to the next entry
    - { provider: claude, model: claude-haiku-5-5 }
    - { provider: codex, model: gpt-5-mini }
  worker: { provider: claude, model: claude-opus-5-5 }
  advisor: { provider: claude, model: claude-opus-5-5, thinking: high }
providers:
  exhausted_for: 1h            # an exhausted provider/model is skipped this long, then tried again (default 1h)
  fallback: [claude/claude-opus-5-5]  # every step falls back to these, after its tier's own entries
agent:
  tier: worker
  mode: bypassPermissions      # steps run unattended (shell commands included)
manager:
  mode: default                # the manager never edits files

defaults/manager.md

When a run ends, give the human the PR link first, then the outcome in one sentence.

roles/babysitter/role.yaml

title: PR Babysitter
readonly: true

roles/babysitter/instructions.md

You are the PR Babysitter of a pull-request playbook.

Watch the pull request's CI checks (`gh pr checks --watch`) and review comments. Combine
them with the review findings and the local QA report.

Choose the outcome `ready` when CI is green and nothing blocking remains. Choose
`changes_requested` otherwise, and put every point the Implementer must fix in your
summary. Do not edit files or push.

roles/gatekeeper/role.yaml

title: Gatekeeper
readonly: true

roles/gatekeeper/instructions.md

You are the Gatekeeper of a pull-request playbook: you decide its loop-limit gate in place
of a human when it is safe.

Allow one more loop ("approved") when the remaining findings are minor (style, naming,
docs, a flaky test) and each loop made progress. Leave the gate to a human ("escalate")
when the same blocker came back twice, or the change touches security, authentication,
billing or data migrations. Do not edit files or push.

roles/implementer/role.yaml

title: Implementer
readonly: false

roles/implementer/instructions.md

You are the Implementer of a pull-request playbook.

Implement the plan in the current checkout. You are already on the run's branch; commit
there and push it. Keep changes focused on the request. Run the relevant tests before
pushing.

Open a pull request against the base branch with `gh pr create`, or update the existing
one if this branch already has a PR. If you received feedback from a previous round,
address every point of it.

Return `pr_url`, `pr_number` and `branch`.

roles/investigator/role.yaml

title: Investigator
readonly: true

roles/investigator/instructions.md

You are the Investigator of a pull-request playbook.

Read the request and the relevant code, history and documentation. Do not edit files,
switch branches or commit. Work out what needs to change and why, and identify risks and
the tests that should prove the change.

Return a concrete implementation plan as the `plan` output: the files to touch, the
approach, edge cases, and how to verify it.

roles/local_qa/role.yaml

title: Local QA
readonly: true

roles/local_qa/instructions.md

You are the Local QA of a pull-request playbook.

Run the project's tests, linters and type checks on the current checkout. Do not edit
tracked files; build output in ignored files is fine. Report what you ran and what failed
as the `report` output, and set `tests_passed`.

roles/reviewer/role.yaml

title: Reviewer
readonly: true

roles/reviewer/instructions.md

You are the Reviewer of a pull-request playbook.

Review the pull request diff (`gh pr diff`) for correctness, security, missing tests and
clarity. Do not edit files or push. Report concrete findings with file and line, ordered
by severity, as the `findings` output. Say "No findings" when the change is good.

Capability (sub-playbooks)

From examples/.paseo/plugins/playbooks/. It builds a change with the Pull request playbook, waits for a human, then releases it with the Release to dev playbook: three steps, two of them sub-playbooks. Rejecting the gate restarts the whole PR block with your comment.

# capability.yaml
title: Capability
description: Build a change with the pull-request playbook, let a human approve it, then release it to the dev environment.

inputs:
  request:
    type: string
    required: true
    description: What to change
  base_branch:
    type: string
    default: main
    description: Branch the PR targets

outputs:
  pr_url: { type: string }       # from the pr block
  env_url: { type: string }      # from the release block

steps:
  # A step with `playbook:` runs another playbook of this folder in place. Its inputs are
  # matched by name (request, base_branch); its outputs (pr_url, pr_number) become this
  # step's outputs. Its steps appear as pr.investigate, pr.implement, …
  - id: pr
    playbook: { name: pr }

  - id: approve
    needs: [pr]
    gate:
      question: The PR is green. Release it to the dev environment, or request changes to rework it.
      choices:
        approved: { label: Release to dev }
        rejected: { label: Request changes, comment: required, color: danger }
    on:
      rejected: { goto: pr }     # restarts the whole pr block, with your comment as feedback

  - id: release
    needs: [approve]
    playbook: { name: release }  # pr_url comes from the pr block

Unattended change

From examples/.paseo/plugins/playbooks/. manager: { mode: none }: no manager agent is created; the plugin starts the steps, applies what they report and stops the run on a failure.

unattended.yaml

title: Unattended change
description: A run with no Playbook Manager agent. The plugin starts each step, applies what the step agents report, stops the run if one fails, and leaves the gates to a human (panel) and to a reviewer role.

manager: { mode: none }        # always_on (default): a manager agent drives the run; none: the plugin does, no manager agent is created

inputs:
  request:
    type: string
    required: true
    description: The change to make

steps:
  - id: implement
    role: { name: implementer }
    timeout: 45m                # with no manager there is no stall handling: the timeout is what stops a step that never ends
    outputs:
      branch: { type: string, description: The branch holding the change }

  # A human gate: shown in the Playbooks panel (Review / Needs you).
  - id: approve
    needs: [implement]
    gate: { question: "Ship {{ steps.implement.outputs.branch }}?" }

  # A role gate: the plugin starts the reviewer itself; it may decide or leave the gate to a human.
  - id: judge
    needs: [approve]
    gate: { question: Is the change safe to merge?, decider: { by: role, role: reviewer } }

  - id: ship
    needs: [judge]
    retries: 1                  # no retry unless the YAML says so
    role: { name: implementer }

Route a change

From examples/.paseo/plugins/playbooks/. A branch step takes the first case whose if holds; only the steps of that case run, and the join runs after it.

route.yaml

title: Route a change
description: Classify a change, then take the branch that fits it (if / else-if / else on a step's output), and join.

inputs:
  request:
    type: string
    required: true
    description: The change to route

steps:
  - id: classify
    role: { name: investigator }
    outputs:
      kind: { type: enum, values: [service, infra, docs], description: What the change touches }
      plan: { type: string, description: The plan for the change }

  # The first case whose `if` holds wins; the last one, with no `if`, is the else.
  - id: route
    needs: [classify]
    branch:
      cases:
        - { name: service, if: { steps.classify.outputs.kind: service } }
        - { name: infra, if: { steps.classify.outputs.kind: infra } }
        - { name: other }

  # Exactly one of these runs; the others are skipped, which counts as done for `needs`.
  - id: ship
    needs: [route]
    when: { steps.route.outcome: service }
    gate: { question: Hand this service change to the release train? }
  - id: apply
    needs: [route]
    when: { steps.route.outcome: infra }
    gate: { question: Merge and apply this infrastructure change by hand? }
  - id: review
    needs: [route]
    when: { steps.route.outcome: other }
    gate: { question: Nothing to ship. Close it? }

  # The join: it starts once the one branch that ran is done.
  - id: done
    needs: [ship, apply, review]
    gate: { question: All done? }

Release to dev

From examples/.paseo/plugins/playbooks/. It deploys the change named by pr_url to the development environment, then checks it there. Used on its own, or as the second block of the Capability playbook.

# release.yaml
title: Release to dev
description: Deploy a change to the development environment and check it there.

inputs:
  pr_url:
    type: string
    required: true
    description: Pull request (or branch) to deploy

outputs:
  env_url: { type: string }      # auto-matched from the release step
  qa_report: { type: string, value: "{{ steps.qa.outputs.report }}" }

steps:
  - id: release
    # The plugin applies a reported success itself and starts qa: the manager is not woken for it.
    role: { name: dev_env_releaser, prompt: "Deploy {{ inputs.pr_url }} to the development environment.", completion: { auto: [success] } }
    inputs: [pr_url]
    outputs:
      env_url: { type: string, description: URL of the deployed dev environment }
      log: { type: string, description: What was run to deploy }
    timeout: 30m

  - id: qa
    # redeploy loops back to release, which the plugin applies; success ends the run, so the manager is woken for it.
    role: { name: dev_env_qa, prompt: "Check {{ inputs.pr_url }} on {{ inputs.env_url }}.", completion: { auto: [redeploy] } }
    needs: [release]
    inputs: [env_url, pr_url]
    outputs:
      report: { type: string }
      passed: { type: boolean }
    outcomes: [success, redeploy]
    on:
      redeploy: { goto: release, max_loops: 1 }

The Release to dev roles, dev_env_releaser and dev_env_qa, deploy and check the change with the process your repository documents, and report a failure when there is none. completion.auto lets the plugin apply the outcomes it lists without waking the manager, as long as an agent or script step follows (reference).

Docs check

From .paseo/plugins/playbooks/ at the root of this repository, the playbook that checks this repository's own docs. Every role only reads or edits files, so default and acceptEdits are enough. The verdict step loops back to the writer at most twice, and a rejected gate sends the work back with your comment.

investigate ─▶ write ─┬─▶ review ──────┬─▶ verdict ─▶ ◆ approve ─▶ end
                 ▲    └─▶ consistency ─┘      │           │
                 └──── changes_requested ─────┘           │
                 └───────────────── rejected ─────────────┘

docs.yaml

title: Docs check
description: Compare the docs with the code, fix the gaps, review and check in parallel, loop until clean, then a human gate.
manager:
  prompt: In the approve gate's details, list each changed document with one line on what changed.

inputs:
  focus:
    type: string
    default: README.md, OVERVIEW.md (and its translations OVERVIEW.fr.md and OVERVIEW.zh-CN.md, which must say the same), skills/paseo-playbooks/SKILL.md and the website/ pages
    description: Which documents to check
  strictness:
    type: enum
    values: [light, thorough]
    default: light
    description: light = only wrong or missing facts; thorough = also clarity

outputs:
  changes: { type: string }                # auto-matched from the write step

steps:
  - id: investigate
    role:
      name: doc_investigator
      prompt: |
        Documents to check: {{ inputs.focus }}
        Strictness: {{ inputs.strictness }}
    inputs: [focus, strictness]
    outputs:
      gaps: { type: string, description: "Numbered list of doc statements that disagree with the code" }
      gap_count: { type: number }

  - id: write
    role:
      name: doc_writer
      agent: { mode: acceptEdits }
      prompt: |
        Fix these gaps in {{ inputs.focus }}:
        {{ inputs.gaps }}
    needs: [investigate]
    inputs: [focus, gaps]
    outputs:
      changes: { type: string, description: "What you changed, per file" }
    timeout: 20m

  - id: review
    role:
      name: doc_reviewer
      prompt: |
        The writer reports these changes (uncommitted in this checkout):
        {{ inputs.changes }}
    needs: [write]
    inputs: [changes]
    outputs:
      findings: { type: string }
      blocking: { type: boolean }

  - id: consistency
    role:
      name: consistency_checker
      prompt: |
        Gaps found earlier:
        {{ inputs.gaps }}

        Changes made:
        {{ inputs.changes }}
    needs: [write]
    inputs: [gaps, changes]
    outputs:
      remaining: { type: string, description: "Gaps still open, or none" }
      all_fixed: { type: boolean }

  - id: verdict
    role:
      name: doc_editor
      prompt: |
        Review findings (blocking: {{ inputs.blocking }}):
        {{ inputs.findings }}

        Remaining gaps (all fixed: {{ inputs.all_fixed }}):
        {{ inputs.remaining }}
    needs: [review, consistency]
    inputs: [findings, blocking, remaining, all_fixed]
    outcomes: [ready, changes_requested]
    on:
      changes_requested: { goto: write, max_loops: 2 }

  - id: approve
    needs: [verdict]
    gate:
      question: The docs are updated, uncommitted. Approve to finish, or request changes to send them back to the writer.
      choices:
        approved: { label: Approve }
        rejected: { label: Request changes, comment: required, color: danger }
    on:
      rejected: { goto: write }

roles/doc_editor/instructions.md

You are the editor who decides whether a documentation change is ready. You read the
review findings and the consistency check you are given; you may read the documents to
confirm. Do not run shell commands and do not edit anything.

Choose the outcome `ready` when nothing blocking remains and every gap is fixed. Choose

roles/doc_investigator/role.yaml

title: Docs investigator
readonly: true

roles/doc_investigator/instructions.md

You check documentation against the code of this repository (a Paseo plugin written in
TypeScript: server/, client/, shared/, examples/).

Read the documents you are given, then the code they describe, using your file reading
and search tools only. Do not run shell commands and do not edit anything.

List every statement in the documents that is wrong, outdated or missing compared with
the code: file paths, field names, defaults, tool names, behaviour. Quote the statement
and say what the code actually does, with the file. With strictness "thorough", also list
unclear passages. Return them as a numbered list in `gaps` and their number in
`gap_count` (0 and "none" if the docs match).

roles/doc_reviewer/role.yaml

title: Docs reviewer
readonly: true

roles/doc_reviewer/instructions.md

You review documentation changes. Read the changed documentation files (they are uncommitted in
this checkout) and the code they describe, with your file reading tools only. Do not run
shell commands and do not edit anything.

Check that every change is accurate, clear and consistent with the rest of the docs.

roles/doc_writer/role.yaml

title: Docs writer
readonly: false

roles/doc_writer/instructions.md

You fix documentation in this repository. Edit only the documentation files you were asked
to check (Markdown files, or the HTML pages under website/), with your file edit tool. In
