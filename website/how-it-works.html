How it works

The plugin owns the deterministic part of a run. The Playbook Manager agent owns the judgment.

Plugin and manager

Plugin (rules)Playbook Manager (judgment)
Loads and validates playbooks, saves run statePicks the playbook that fits the request
Computes which steps are ready, resets loops, enforces limitsWrites each step's brief and reads its result
Creates step agents with their role, prompt and labelsChooses each outcome, and whether to retry, nudge or loop
Wakes the manager when a step finishes or a gate is decidedSummarises the run for the human at a gate

The manager never edits run state directly. It calls the plugin's tools, and the plugin refuses anything the playbook does not allow, such as starting a step that is not ready.

Lifecycle of a run

  1. Start. Start runs the playbook with the workspace's current agent, which becomes the manager. The arrow next to it offers Start on a new agent and Start in a new workspace (a worktree on a new branch playbooks/<playbook>-<short id>, so the run never touches your checkout). One active run per workspace, unless the playbook has isolation: worktree (see isolated runs).
  2. Steps. Every ready agent step starts by itself, with an empty brief; a step with manage: { auto_start: false } waits for the manager to call start_step with a brief. The plugin creates a subagent in the same worktree, with the role as system prompt and the rendered prompt, inputs and brief as first message.
  3. Report. The step agent calls report_step_result with an outcome, a summary and its typed outputs, then ends its turn.
  4. Wake-up. The plugin checks readonly roles with git, then wakes the manager once it is idle. The manager is woken only for what it must decide or what went wrong (a report, a failure, a gate, a step waiting for a brief, a stall, the end of the run), not for every step; manage: { notify: true } opts a step in. Wake-ups are merged into one prompt; the manager's turn is never cancelled.
  5. Decide. The manager calls complete_step. The plugin applies the transition and returns what is ready next, a gate to open, or the end of the run.
  6. Gate. The manager opens a ready gate with request_gate and ends its turn. You decide in the panel, and the manager is woken with your decision.
  7. End and wrap-up. The run completes, fails or is canceled. after: tasks then run: auto ones on their own, manual ones from a button. They never change the run's status.

Tools

Plugin tools reach agents through Paseo's MCP server. For Claude agents the plugin creates, it pre-approves its own tools, so default mode agents are not stopped by a permission prompt on them. Other providers may still ask. An agent gets the manager tools when its workspace has a playbook, when it already manages a run, or when Start created it.

Step, gate and Sidekick

  • Step agents get only report_step_result. Gate agents get only report_gate_decision. In a run with no manager, step agents also get answer_gate.
  • The Sidekick gets sidekick_handoff, which saves its decision ledger and notes; with restart: true a fresh session replaces it when its turn ends.

Run state

  • Each run is one JSON file in $PASEO_HOME/plugin-data/lerenn/paseo-playbooks/runs/, written atomically: playbook snapshot, inputs, every step's attempts, reports and outputs, gates, loop counts and history. Runs survive daemon restarts and plugin reloads.
  • On start, steps whose agents stopped without reporting are marked lost and the manager is told. A run whose manager no longer exists is failed, and can be recovered with restart_run.
  • If the manager is archived during a run, the run fails with "manager lost (archived)". The exception is a manager archived along with the agent that created it: a new Playbook Manager takes the run over, and completed steps keep their outputs.
  • A completed or canceled isolated run's worktree and branch are removed (see isolated runs). Step agents are archived when no longer needed if role.archive_agents is true (the default).
  • If a step fails because its provider is out of tokens and its tier lists several providers, the attempt restarts on the next one. The exhausted provider/model is skipped for providers.exhausted_for (default 1h). Before starting, the plugin also skips a provider whose reported usage is already full (providers.usage), for every run on the host.
  • A fan-out step with a pool stays open while it runs. The plugin's scan (every two seconds, no agent) notices ended children and, one at a time, starts a refill pass: a run of the pool's playbook in its own workspace, given the keys of the finished items. When it completes, the items it lists that are not yet children are added in one state change (diffed by key, so repeating a pass is harmless) and start under max_active. The pass is recorded in the step's state (number, finished keys given, items added), so a daemon restart follows it or runs it again; the main step state is never rewritten by a pass.
  • Two limits: a plugin reload removes the playbook tools from running agents until their next message, and a busy agent's queued kickoff is kept in memory only, so a daemon restart before it is delivered leaves the run with nothing driving it (cancel it and start again).

The Playbooks panel

  • Opens in the workspace's right-hand sidebar, or with Ctrl+K (Cmd+K) → Open Playbooks. It works on desktop, web and mobile.
  • Each playbook is a card with its title, path, validation errors and a Start button. Start opens a form built from the playbook's typed inputs, warns about an active run with the same inputs, and refuses past the concurrency limit.
  • The graph runs top to bottom, with parallel steps side by side and loops as dashed lanes back up. Nodes show their state: running pulses, completed is green, failed red, gates and permission requests amber, unreached dimmed. After-tasks sit below End.
  • Press a node to open its agent's conversation; #1 #2 chips open earlier attempts, and ⓘ opens inputs, the manager's brief, the report and the role instructions.
  • Each run has a menu to Pause or Resume (running steps finish, nothing new starts), Cancel, and Archive once finished. A finished run can be restarted from a step with Restart run from here.
  • Gates show one button per choice (Approve and Reject by default), some with a comment field.

Limits with Paseo 0.14

  • The plugin uses Paseo 0.14's server.on and server.before hooks. The panel refreshes on agent updates (batched over 400 ms), with a 30-second backstop poll for changes that raise no agent event, such as a step timeout.
  • The SDK has no call to cancel a turn; the plugin stops a step agent by reloading its session.
