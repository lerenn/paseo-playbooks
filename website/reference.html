Playbook reference

Everything the plugin reads from your repository, and the rules it checks before a playbook can run. Each entry ends with an example; complete playbooks are in examples/ on GitHub.

Folders and layout

The plugin reads two folders in the workspace: .paseo/plugins/playbooks/ and .paseo/playbooks/. Both are loaded and merged. Each folder is self-contained: a playbook uses the roles/ and defaults/main.yaml of its own folder. The same playbook id in both folders is an error on both files.

.paseo/plugins/playbooks/
├── defaults/
│   └── main.yaml          # optional: agent defaults for this folder
├── pr.yaml                # a playbook; its id is the file name ("pr")
├── release.yaml
└── roles/
    └── reviewer/
        ├── role.yaml      # title, readonly, agent
        └── instructions.md
Details
  • Every top-level *.yaml or *.yml file is a playbook. Shared settings live in subfolders, so no file name is reserved.
  • Profiles: profiles/<name>/ in .paseo/plugins/playbooks/ is an extra, opt-in repository with the same layout as the folder itself (the default repository, on unless a project turns it off). Turn profiles on per project, in the Profiles tab of the Playbooks screen or the dropdown in the Playbooks panel; they are off by default, the choice applies to every workspace of the project and is stored per user. A profile's playbook is named <profile>:<id> (louis:deploy) and uses only its own roles and sub-playbooks. A bare id shared by two repositories is ambiguous: write default:deploy or louis:deploy.
  • Ids (playbooks, roles, steps, inputs, outputs) use lowercase letters, digits, - and _, starting with a letter.
  • Playbooks are read from the workspace's own folder, so a branch or worktree can carry its own changes. Start stores a copy of the resolved playbook in the run, so editing files does not change runs in progress.

Example: pr.yaml

title: Pull request
description: Investigate a request, implement it, open a PR.
manager: { prompt: Check that the PR targets the base branch. }
isolation: worktree
concurrency: 2
inputs:
  request: { type: string, required: true }
outputs:
  pr_url: { type: string }
steps:
  - id: implement
    role: { name: implementer, prompt: "{{ inputs.request }}" }

Step fields

A step is an agent step (role), a human gate (gate), a script step (script), a sub-playbook (playbook) a hand-off to a singleton playbook (handoff), a branch (branch) or a fan-out of one run per list item (fanout, see fan-out steps), exactly one of them. The kind's key holds a block with the options of that kind; the other fields sit on the step. The order of steps in the file does not matter.

- id: review
  role: { name: reviewer, prompt: "Review {{ inputs.pr_url }}" }
- id: approve
  gate: { question: "Ship it?", choices: { ship: ~, hold: { comment: required } } }
- id: wait_ci
  script: { run: wait_ci.sh, poll: 10m, wake_on: [{ types: [job.settled], filter: { playbook: other_pipeline } }] }
- id: release
  playbook: { name: release }

role.nameagentRequired. Role folder name under roles/.

role.silenceagentAfter this long without agent activity, the plugin asks the agent once to report or say what it is waiting for, and tells the manager. Default role.silence of defaults/main.yaml, else 30m; off disables it.
role.archive_agentsagentArchive the step's agents once the run no longer needs them: when the step completes or its run or after-task ends, and an attempt's agent when the next attempt starts. Default role.archive_agents of defaults/main.yaml, else true; false keeps them, to debug for example.

Each block refuses keys it does not know. The plain-string forms (role: reviewer, gate: "Ship it?") and the old flat fields (prompt, silence, archive_agents, agent, choices, poll on the step) are invalid; the error says what to write instead, for example role: write `role: { name: reviewer }`.

Variables

KeyMeaning
typestring (default), number, boolean, enum or list (a JSON array, see List values). There is no object type; a list's items may be flat objects.
valuesAllowed values, for enum only (required there).
requiredPlaybook inputs: the run cannot start without a value.
defaultValue used when none is given.
descriptionShown in the Start form and to agents.

Numbers and booleans sent as text ("42", "true") are accepted. A report that misses a declared output or has the wrong type is refused, with the reason, so the agent fixes it in the same turn. The one exception is a failure report, which skips output validation, so a failed step may leave its outputs empty.

Example: pr.yaml

inputs:
  request: { type: string, required: true }
  env: { type: enum, values: [dev, stg, prd], default: dev }
  dry_run: { type: boolean, default: false }
  targets: { type: list }          # a JSON array of strings
outputs:
  pr_number: { type: number, value: "{{ steps.implement.outputs.pr_number }}" }

Where a step input comes from

Playbook outputs without value are matched the same way, from any step with a same-named, type-compatible output. Any type can feed a string. The detail sheet shows where each value came from, for example pr_url ← implement.pr_url (auto).

Details
  1. An explicit source wins: "{{ playbook.inputs.x }}" or "{{ steps.<id>.outputs.y }}", where the step must be one this step needs, directly or not.
  2. Otherwise the input takes the output with the same name from a step it needs, directly or not.
  3. Failing that, it takes the playbook input with the same name.
  4. If several earlier steps output that name, or nothing matches, the playbook is invalid until you map the input explicitly. Nothing is chosen silently.

Example: pr.yaml

- id: babysit
  needs: [review, local_qa]
  inputs:
    pr_url: ~                                       # matched by name from implement
    review: "{{ steps.review.outputs.findings }}"   # explicit
    base: "{{ playbook.inputs.base_branch }}"       # explicit, from the playbook

Prompt templates

Templates use plain {{ path }} substitution, with no conditionals or loops. A step prompt may use only {{ inputs.<name> }} (a declared input; the inputs: map uses the other forms, {{ playbook.inputs.x }} and {{ steps.<id>.outputs.y }}), {{ run.id }}, {{ worktree }} (the run's worktree when it is isolated, else the workspace directory; also usable in a role's instructions.md), {{ run.jobs }} (a singleton batch's open jobs, as YAML) and {{ attempt }} (retries) and {{ loop }} (how many times a goto sent the run back through this step; 0 on the first pass); steps of an after-task may also use {{ run.status }} and {{ run.failure }}. Missing or empty values render as (none). If a prompt has no placeholders, the plugin lists the step's inputs after it. The manager's brief and any loop feedback are appended to the prompt.

Example: pr.yaml

role:
  name: implementer
  prompt: |
    Request: {{ inputs.request }}
    Work in {{ worktree }}. Attempt {{ attempt }}, loop {{ loop }}.

Roles

A role is a folder roles/<id>/ with two files. A playbook refers to it by its folder name, and several playbooks can share it.

File / keyMeaning
instructions.mdRequired and non-empty. The system prompt of every step that uses the role. The plugin appends the step protocol: allowed outcomes, required outputs, and how to call report_step_result.
role.yaml titleDisplay name. Defaults to the id.
role.yaml readonlytrue if the role must not edit files. Default false. See readonly roles.
role.yaml agentAgent settings for this role.

Example: roles/reviewer/

roles/
  reviewer/
    instructions.md      # the system prompt: "You review code. Do not edit files."
    role.yaml

# role.yaml
title: Reviewer
readonly: true
agent: { tier: cheap }

Outcomes and flow

Details
  • The step agent reports an outcome with report_step_result. The manager then decides the final outcome with complete_step, and may correct the outputs.
  • One rule for agent steps and gates: the first listed outcome (a gate's first choice) completes the step by default. Steps whose needs are now all completed become ready.
  • failure makes the step ready again while attempts remain (retries), then fails the run. Attempts lost in a daemon restart do not count.
  • Every other outcome needs an on entry (complete, end, fail, goto or, for agent steps, ask); without one, validation fails. The one exception is a gate without choices: its default rejected fails the run.
  • end ends the playbook it is written in: the run at top level, the block when the playbook is nested (see sub-playbooks), the task inside an after-task. The run completes when every step has completed (or was skipped), or on a top-level end; its outputs are then resolved. fail fails the run at once.
  • A timeout interrupts the step agent's turn. Retries apply only after the manager completes the step with the failure outcome.

Example: pr.yaml

- id: babysit
  needs: [review]
  role: { name: babysitter, prompt: "Get {{ inputs.pr_url }} green." }
  outcomes: [ready, changes_requested, abandoned]   # the first one completes the step
  retries: 1                       # on failure
  on:
    changes_requested: { goto: implement, max_loops: 3 }
    abandoned: { end: true }       # ends the playbook it is written in
    ready: { complete: true }

Gates

A gate becomes ready like any step. The manager opens it with request_gate: a one-sentence summary shown on the gate, and details (your gate.question, then the manager's notes) collapsed under it. Its buttons come from gate.choices, in order: each key is an outcome, with a label, comment: none | optional | required and color: primary | neutral | success | warning | danger (Paseo theme colours; by default the first choice is primary and the others neutral). Without choices, a gate offers approved (Approve) and rejected (Reject, optional comment, colour danger). The first choice completes the gate by default. A gate that declares choices needs an on entry for every other choice; only the default Reject fails the run without one. Each button shows where it leads (→ End, → End Release inside a block, → Implement, → Fail run). A choice that takes a comment opens a text box with Send; the comment goes to the manager and, on a goto, to the target as feedback. Decisions come from the panel, or by chat through the manager's resume tool. The first decision wins.

- id: pr_approval
  needs: [babysit]
  gate:
    question: The PR is ready. Approve to finish, or request changes to send it back.
    choices:
      approved: { label: Approve }
      rejected: { label: Request changes, comment: required, color: danger }
  on:
    rejected: { goto: implement }

Who decides a gate

Every gate is a human gate unless it names a decider: a gate step in its gate: block, an ask in its transition, and a loop-limit gate on the goto that has max_loops (on a goto without it, decider is an error; the loop-limit gate of an ask choice follows the ask's). A human can always decide first in the panel.

- id: approve
  gate: { question: Ship it?, decider: { by: role, role: gatekeeper } }
# on an agent step:
on:
  unsure: { ask: "Which way?", decider: { by: manager } }
  changes_requested: { goto: implement, max_loops: 3, decider: { by: role, role: gatekeeper } }
byWho decides
humanDefault. The manager asks the human in chat and relays the answer with resume, or the human decides in the panel.
managerThe manager may decide alone with resume and byManager: true, giving its reason as comment (shown as "by the manager"), or ask a human as for a human gate.
roleWhen the gate opens, the plugin starts an agent with role (it must be readonly). It gets the gate, its choices, the run's inputs and the steps' summaries and outputs, and calls report_gate_decision with a choice or escalate, and its reason. If it escalates, ends without deciding (after one reminder) or is archived, the gate goes to a human with its reason in the details. Until then the gate does not count as waiting for you.

Loops

Details
  • goto must point to the step itself or to a step it needs, directly or not. Loops are the only backward edges.
  • A goto resets the target and every step downstream of it to pending, clears their outputs, and interrupts any of their agents still running. The target becomes ready again.
  • The summary of the step that looped, or the gate comment, is added to the target's next prompt as "Feedback to address". An approved loop-limit gate adds its decision comment after the summary; a comment from the manager or a role decider says who wrote it (the manager decided: …), on every kind of gate.
  • on: { <outcome>: { ask: "...", goto: <step>, max_loops: N } } (agent steps) lets a step ask a human. Completing the step with that outcome opens a gate with your ask text and the step's summary (the question); the human's answer is required and becomes the feedback of goto's target, which defaults to the step itself. The report needs no outputs (those it gives are kept), and max_loops works as for goto. Example: outcomes: [success, needs_input] with on: { needs_input: { ask: "The investigation needs your input." } }.
  • choices on an ask gives its gate several buttons, each going to its own step: blocked: { ask: "QA is blocked.", choices: { answered: {}, fix: { goto: fix }, skip: { comment: none } } }. Each choice takes goto (default: the ask's goto, else the step itself), max_loops (default: the ask's), label, color and comment (none, optional or required, the default). The target gets The human answered "<id>": <comment> as feedback. Without choices the gate has a single "Send answer" button (answered) and the target gets the answer alone.
  • An ask choice with outcome ends the asking step with that outcome instead, without running it again: the outcome's on entry applies (complete, end, fail or goto, not ask), and goto and max_loops do not apply. Its outputs set the step's outputs over those of the last report, as templates over {{ gate.comment }}, {{ gate.choice }}, {{ report.summary }}, {{ report.outputs.<output> }} and {{ inputs.<input> }}; a missing output refuses the decision. Example: continue: { outcome: success, comment: optional, outputs: { accepted_unverified: "{{ gate.comment }}" } }.
  • max_loops counts how many times that edge fired. At the limit the plugin opens a "loop limit" gate: approve allows one more loop, reject fails the run. Inside a block, the count restarts from 0 each time a goto from outside re-enters the block, so an outer loop over items gives every item its own max_loops; the outer goto's own count keeps going, and {{ loop }} is not reset.

Example: pr.yaml

- id: qa
  needs: [implement]
  role: { name: qa, prompt: "Test the change." }
  outcomes: [success, failed, needs_input]
  on:
    failed: { goto: implement, max_loops: 3 }   # a loop-limit gate opens at the 4th
    needs_input: { ask: "QA needs your input.", goto: implement }

Conditional steps

when runs a step only for some values of the run's inputs (inside a sub-playbook, of the block's inputs): when: { env: prd }, or a list, when: { env: [stg, prd] }. Values are checked against the input's type; there is no expression language. A step whose condition does not hold is skipped as soon as it would be ready, and counts as done for the steps that need it. Its outputs are unset, so a later step may read them only if it has the same when. A when on a playbook step applies to every step of the block.

when: { loop: ">=2" } tests the step's own loop count instead of an input: a number (equals), a comparison (">=2", "<3", "==1") or a list (any holds). An input named loop wins over it, and it does not apply to a playbook step.

steps:
  - id: go
    when: { env: prd }        # only prd asks for a human go
    gate: { question: Release to prd? }
  - id: release
    needs: [go]               # on dev, starts at once
    role: { name: env_releaser }

Branches: if / else-if / else

when also tests what earlier steps found: steps.<id>.outputs.<name> or steps.<id>.outcome (the step must come before it through needs). A test is a value, a list (any of), or { empty: true } / { empty: false }; all tests of one when must hold.

steps:
  - id: route
    needs: [approve]
    branch:
      cases:
        - { name: service, if: { steps.prs.outputs.kind: service } }
        - { name: other }                    # the else
  - id: trains
    needs: [route]
    when: { steps.route.outcome: service }
    role: { name: releaser }
  - id: by_hand
    needs: [route]
    when: { steps.route.outcome: other }
    gate: { question: Merge and apply by hand? }
  - id: done
    needs: [trains, by_hand]               # the join
Details

A branch step lists cases in order. The plugin takes the first case whose if holds (the last has no if: the required else) and completes the step with that case's name as its outcome. Steps of a case test it in when; the others are skipped, and a skipped step counts as done, so a later step that needs all of them is the join. The validator refuses a missing or misplaced else, an unreachable case, duplicate names, and unknown steps, outputs, outcomes or values; a branch does not apply to after-tasks or singleton stages. A case may end the run with end: true or end: <outcome>. A gate question and an ask text may read {{ playbook.inputs.<name> }} and {{ steps.<id>.outputs.<name> }} of earlier steps.

Sub-playbooks

A step with playbook: { name: <id> } runs another playbook of the same folder in place, as a building block. The loader expands it: its steps become pr.investigate, pr.implement… in the same run, under the same manager, and the panel draws a labelled frame around them.

steps:
  - id: pr
    playbook: { name: pr }       # inputs match by name, or map them in `inputs`
  - id: approve
    needs: [pr]
    gate: { question: Release it? }
    on:
      rejected: { goto: pr }     # restarts the whole block, with the comment as feedback
  - id: release
    needs: [approve]
    playbook: { name: release }  # gets pr_url from the pr block's outputs
Details
  • The block's first steps take its needs; steps that need the block wait for its last steps.
  • Its inputs are the sub-playbook's inputs, auto-matched by name or mapped in inputs; unmatched ones use their default. Its outputs are the sub-playbook's outputs, usable by name or as {{ steps.pr.outputs.pr_url }}.
  • Loops inside the sub-playbook stay inside. A goto to the block restarts it from its first step; the sub-playbook must have exactly one.
  • end ends the playbook it is written in, so inside the sub-playbook it ends the block, not the run: the step completes, the block's other unfinished steps become skipped (running ones are interrupted; the panel dims them), and the steps that need the block go on. In nested blocks it ends only the innermost one. The block's outputs are what its completed steps produced. fail still fails the whole run. A goto to the block runs it again.
  • outputs, outcomes and timeout do not apply to a playbook step; its on takes only complete, end and fail. A playbook that includes itself, directly or not, is an error.
  • The sub-playbook's manager settings are ignored; its gates stay gates of the run.
  • The sub-playbook's concurrency applies to the block. Its slots are shared by every run in the project, including top-level runs of that playbook. A run takes a slot when the block's first steps become ready and keeps it until all the block's steps complete or are skipped (also while a gate inside waits) or the run ends. Until then those steps are queued ("waiting for a free slot" in the panel) and the manager is woken when they are ready. A goto that restarts the block's first steps releases the slot and queues again.

Sub-playbooks are the only way to combine playbooks: one run and one graph, so a gate or a loop can sit between two playbooks. There is no chaining from one run to another.

After-tasks

after: lists tasks that run once the run has ended, whatever its outcome: a retro that reflects on the run, a notification. Each task is an agent step (role with its prompt), a gate, or a sub-playbook (playbook: { name: <id> }), with a trigger.

after:
  - id: retro
    playbook: { name: retro }
    inputs:
      run_id: "{{ run.id }}"   # run values are always mapped explicitly
  - id: notify
    role: { name: reviewer, prompt: "Post a summary of run {{ run.id }} ({{ inputs.status }})." }
    trigger: manual      # default: auto
    inputs:
      status: "{{ run.status }}"
Details
  • They belong to the same run: same run file, same manager, drawn below End in the panel graph, each in its own frame.
  • They never change the run's status, which is fixed when the main graph ends. Inside an after-task, end completes the task (it ends the playbook it is written in); fail, exhausted retries or a rejected gate fail the task only. In a sub-playbook used as an after-task, a nested block's end still ends only that block.
  • auto (the default) starts when the run completes or fails, not when it is canceled. manual shows a Start button on the finished run, in any end state; each manual task runs once. The manager is woken with the task's ready steps.
  • No needs: each task starts on its own, and several may run at once.
  • Inputs may also use {{ run.id }}, {{ run.status }}, {{ run.failure }}, {{ run.outputs.<name> }} (the run's outputs; partial on a failed run) and the outputs of any main step. By name, an input matches the playbook's outputs, then the playbook's inputs, as elsewhere. Run values never match by name: write run_id: "{{ run.id }}". Prompts may use {{ run.status }} and {{ run.failure }}.
  • A sub-playbook's own after is ignored when it is nested: only the outermost playbook's after-tasks run. A sub-playbook used as an after-task keeps its steps, gates and loops; its concurrency is ignored, and after-tasks hold no concurrency slot.
  • While after-tasks run, the run is "wrapping up": its dot pulses in its final colour, it stays active in its workspace, and Cancel cancels the after-tasks without changing the run's status. Archiving the worktree or losing the manager does the same.
  • The "both may edit files" rule applies between after-tasks, not between an after-task and a main step.

List values and fan-out steps

A variable of type list is a JSON array of strings, numbers, booleans or flat objects (at most 200 items, 32,000 characters), stored and rendered as JSON text: {{ steps.x.outputs.items }} shows it anywhere, a gate question included. A script reports one as an array in its last line's outputs.

- id: spawn
  needs: [list]
  inputs: { items: "{{ steps.list.outputs.items }}" }
  fanout:
    playbook: batch_item
    items: "{{ inputs.items }}"
    key: "{{ item.id }}"
    inputs: { item_id: "{{ item.id }}" }
    workspace_name: "Batch: {{ item.id }}"
    max_active: 3
    cancel_children: true
  on: { some_failed: complete }
Details

A fan-out step starts one run of a playbook of the same folder per item, each in its own new workspace with its own manager, at most max_active at once, and completes when all have ended.

Outcomes: all_completed, some_failed (any child failed, was canceled or not started; fails the run unless on routes it) and failure. A failing child never stops its siblings. Outputs: results (list of {key, runId, outcome}), total, started, completed, failed, canceled, not_started, any_failed. A child is never started twice for one key, restarts included. Canceling or failing the parent (or resetting the step) cancels the active children unless cancel_children: false. The run view draws one lane per child, with earlier passes of a loop kept.

Agent settings

provider, model, mode and thinking merge field by field. Precedence: step (role.agent) > role > playbook > defaults/main.yaml > the manager's own provider and model. With no model at all, Claude steps use Claude Opus.

Details

A tier (tiers: in defaults/main.yaml) names a set of these fields. Any agent block (the defaults' agent and manager, a playbook, a role's role.yaml, a step's role.agent, a role decider's decider.agent) can write agent: { tier: cheap }: the tier's fields come first, the block's own fields override them, then the layers merge as above. An unknown tier is an error. Switching from Claude to Codex is one edit of the tiers.

A tier may be a list of targets, each with provider, model, mode, thinking: the first is the primary, the rest are fallbacks. When a step agent's turn fails because its provider is out of tokens (quota, rate or usage limit, no credits), the plugin restarts the same attempt on the next entry with the same brief, without using a retry, records the exhausted provider/model in run.exhausted ({ target, at }) and skips it for providers.exhausted_for (default 1h; limits reset, so it is tried again after that, and very short values re-probe a failing provider), logs a provider_exhausted line and tells the manager (who is told when it is tried again). When every entry is exhausted the failure goes to the manager as usual, unless providers.on_exhausted is wait: the step then stays running, shown as "Waiting for tokens until HH:MM", and the plugin restarts the same attempt (no retry used) once a provider is due again, waiting again if it is still out, until providers.max_wait (default: no limit) is spent and the failure goes to the manager. A multi-entry tier cannot be combined with inline provider, model, mode or thinking on the same block: define another tier. On manager it only picks the first entry when a manager is created.

providers.fallback, a list of provider/model, is added to every step agent's chain after its tier's own entries, so a role with a single model moves on too; a fallback keeps the role's mode and thinking only on the same provider. Out of tokens is detected on a failed turn and on a turn that ends on the provider's short notice ("You've hit your weekly limit · resets Nov 16, 2pm"). The manager can also choose a model for one attempt: start_step, nudge_step and restart_run take model (provider/model, checked against the provider's models) and thinking; with nudge_step a new agent on that model takes over the same attempt, without using a retry. get_run shows each step's model, and per attempt its agents and models in view full.

Example: defaults/main.yaml

# defaults/main.yaml
tiers:
  cheap:                         # a list: the second is a fallback
    - { provider: claude, model: claude-haiku-5-5 }
    - { provider: codex, model: gpt-5-mini }
  worker: { provider: claude, model: claude-opus-5-5, thinking: high }
providers: { exhausted_for: 1h }
agent: { tier: cheap }

# a step that needs more
role: { name: implementer, agent: { tier: worker, mode: bypassPermissions } }

Agent modes

A playbook may use any agent mode, bypassPermissions included: steps that run shell commands then work without asking. Playbooks come from the repository, so any branch can ship one; only start playbooks from repositories you trust. An unset mode uses the provider's default.

Example: defaults/main.yaml

agent:
  mode: bypassPermissions      # steps run shell commands without asking

Isolated runs

By default a run works in its workspace's checkout, so a workspace holds one active run. With isolation: worktree (a playbook field, or a default in defaults/main.yaml) the plugin creates a git worktree for each run under $PASEO_HOME/plugin-data/lerenn/paseo-playbooks/worktrees/<runId>, on a new branch playbooks/<playbook>-<id> off a freshly fetched origin/<base> (base defaults to the project's default branch). When the run ends, the worktree is removed, except when the run failed and workspace.keep_failed is true (the default), which keeps it for inspection. It is also kept when it has uncommitted changes or when the isolation guard fired, and a branch with commits on no remote is always kept; see Cleanup below.

Details
  • Agents are told, not moved. Paseo pins an agent's directory to its workspace, so the run stays visible and busy in the original workspace. Every manager and step agent gets a preamble: the worktree's absolute path, run every command from it (cd <path> && ... or git -C <path>; the shell resets between commands), use absolute paths for Read, Edit and Write, never edit the workspace checkout. Role prompts with relative paths keep working; {{ worktree }} gives the path where a prompt needs it.
  • Guard. When each step ends, and when the run ends, the plugin compares the workspace checkout's HEAD and git status with their state at run start. A change fails the step (isolation guard, naming the changed paths). The readonly check of a readonly role covers the worktree.
  • Submodules. submodules: none (default) leaves them empty; agents run git submodule update --init -- <path> for the ones they need. all or a list of paths links each as a detached worktree of the workspace's own clone, at the commit the worktree pins.
  • Cleanup. A completed or canceled run's worktree and branch are removed. They are kept, with a history entry, when the run failed and workspace.keep_failed is true, when the worktree has uncommitted changes, or when the guard fired; a branch with commits on no remote is always kept. Restarting a run recreates its worktree. At daemon start the plugin removes worktrees whose run no longer exists, and it never deletes outside its worktrees directory.
  • Gitlink guard. When each step ends, the plugin checks the run's branch against its base: if it deletes a submodule entry (mode 160000), the step fails, naming the paths. isolation: { allow_gitlink_removal: true } turns the check off (default false). Agents are also told never to run git add -A, git add . or git commit -a.
  • Concurrency. Isolated runs share a workspace. A run without isolation still needs it to itself, and is refused while an isolated run is active there, and the other way round. Singletons and release batches are never isolated.

Example: pr.yaml

isolation:
  mode: worktree
  submodules: none            # or all, or [paths]
  base: main                  # default: the project's default branch
# shorthand: isolation: worktree

Readonly roles and concurrency

Details
  • Before a readonly step starts, the plugin records the checkout's HEAD and git status --porcelain, including untracked files. When the step ends it compares them. Any change fails the attempt with "readonly role modified the checkout". Build output in ignored files does not count.
  • Steps share the run's worktree. Two steps that can run at the same time (neither needs the other) must not both be able to edit files: make one role readonly or order them with needs.

Example: roles + steps

# roles/reviewer/role.yaml
readonly: true

# review and local_qa run together: only one of them may edit files
- { id: review, needs: [implement], role: { name: reviewer, prompt: "Review." } }
- { id: local_qa, needs: [implement], role: { name: local_qa, prompt: "Test." } }

Runs with no manager

manager: { mode: none } (default always_on; also manager: { lifecycle: none } in defaults/main.yaml) runs a playbook with no manager agent. The plugin starts the ready agent steps as top-level agents of the workspace, applies every outcome a step agent reports (the YAML's retries, on and goto decide what follows), opens a human gate in the panel, starts the decider of a role gate (a by: manager gate is a human's), and stops the run in its failed state when a step fails, ends without reporting, times out, cannot start or loses its agent. The silence reminder does not exist: only a step's timeout stops one that never ends. start_step, complete_step, nudge_step and request_gate are refused on such a run; restart_run works. A human gate is shown in the panel and, when the step agent just before it is still alive (role.archive_agents: false, idle), also put to the human in that agent's conversation: the plugin asks it to use AskUserQuestion and then answer_gate. Answering in either place closes the gate; the other one is told it is stale. See the unattended example.

Details

The Playbook Manager has no role: its protocol is fixed. defaults/manager.md holds repo-wide instructions for the manager of every run of its folder; an empty file makes every playbook of the folder invalid. A playbook adds its own with manager: { prompt }. The manager gets them after its protocol, never instead of it, as a list: the repository's first, then the playbook's, then each sub-playbook's (in steps or after-tasks, at any depth, each playbook once), labelled repository: or with the playbook id. They come in start_playbook's result, or in the kickoff when the panel hands a run to a manager. A batch's manager gets the repository's, the singleton's and its own stage's sub-playbooks'.

Example: unattended.yaml

title: Unattended change
manager: { mode: none }        # the plugin drives the run
steps:
  - id: change
    role: { name: implementer, prompt: "Make the change." }
    outcomes: [done, blocked]
    on:
      blocked: { fail: true }
  - id: approve
    needs: [change]
    gate: { question: Ship it? }   # a human decides, in the panel

Singleton playbooks and hand-offs

A singleton playbook is a pipeline that takes work (jobs) from other runs: one long-lived run per project, in one shared workspace. Its top-level steps are stages, ordered by needs; jobs move through them. Its inputs, outputs and outcomes are each job's.

title: Release trains
singleton: { branch: main }           # its workspace branches off it
inputs:
  pr_url: { type: string, required: true }
outputs:
  report: { type: string }
outcomes: [shipped, ejected]
steps:
  - id: dev
    playbook: { name: train }
    inputs: { env: dev }              # constants only
    queue: { mode: merge }            # every waiting job is in the same batch
  - id: stg
    needs: [dev]
    playbook: { name: train }
    inputs: { env: stg }
    queue: { mode: merge }
  - id: prd
    needs: [stg]
    playbook: { name: train_prd }
    queue: { mode: merge }
    retries: 3                        # failed batches a job may be retried here
  - id: release
    needs: [approve]
    handoff: { name: release_trains }
    inputs: { pr_url: ~ }
    timeout: 5m                       # only to hand the job over
Details
  • Stages. Each has a waiting list and runs one batch at a time. A batch is an ordinary run of the stage's steps, with its own Playbook Manager in the shared workspace; the stage's previous manager is archived when the next batch leaves. Stages run in parallel.
  • queue: { mode }. fifo (default) takes the oldest waiting job alone; merge takes every waiting job (a merge queue).
  • Admission. queue: { admit: { script, poll } } runs a script on the waiting list that decides, per job, who may join the next batch.
  • Moving on. When a batch completes, its jobs still open pass the stage and wait at the next ones; a job that passed every stage leaves with the first outcome, its outputs all set. When a batch fails, its jobs wait at the stage again, at the front, up to its retries, then fail. goto between stages is refused.
  • Jobs in steps. Steps read the batch's jobs (inputs, and outputs set at earlier stages) through {{ run.jobs }} (PLAYBOOK_JOBS for scripts). A stage's inputs take constants, which its sub-playbook reads as inputs.
  • Settling. The batch's manager calls settle_job: without an outcome to set a job's outputs, with one (ejected) to end it now, or an outcome the playbook declares in the step's settle.effects: continue (it stays in the batch) or requeue (it leaves the batch for its stage's queue with no failed ride; reason and an optional opaque blocker; queue.max_requeues caps it). A stage with queue.admit can hold it until the blocker is gone.
  • Every role must be readonly (batches share one checkout). No concurrency, no after; a singleton is never a sub-playbook or an after-task. When no batch runs, its workspace is fast-forwarded to branch and its playbook read again.

A hand-off step gives a job, and with it the task, to a singleton. It is not a sub-step: once the pipeline has taken the job the step is done and the run goes on (typically it ends there):

A hand-off has no outputs and no on: the run does not wait for the other playbook and receives nothing back (outputs, on and the old handoff.wait are refused with an error saying so, and reading steps.<id>.outputs.* from it is refused). The plugin starts and completes it with the singleton's first outcome, or failure if the job cannot be handed over. The job then belongs to the pipeline: it survives the run completing, failing, being canceled or reset, and how it ends is recorded on the pipeline only. The run keeps the trace: the hand-off's attempt records the target and the job id, shown on the step in the panel. A hand-off that leads back to its own playbook is refused.

To rework an ejected job, the batch's manager calls start_playbook with newWorkspace: true: the new run gets its own workspace and Playbook Manager.

The panel and the Playbooks screen show a singleton's stages (waiting list and current batch) and its batches; a hand-off step shows where its job is.

Admission on a stage's queue

A job's precondition (QA passed, a dependency deployed, a ticket state) may fail while the others are fine. A stage's queue can run a script that decides, per waiting job, who may join its next batch. No batch, manager, agent or tokens are involved: the plugin runs the script itself, like a script step.

  - id: staging
    needs: [dev]
    playbook: { name: train }
    queue:
      mode: fifo
      admit:
        script: admit_staging.sh          # an executable of scripts/
        poll: 10m                         # required: the safety net
        wake_on:                          # optional, as for script steps
          - { types: [job.advanced, job.settled], filter: { playbook: qa_pipeline, stage: smoke } }
Details
  • When it runs. While jobs wait at the stage: at the first look (and after a daemon restart: the check reruns, so it must be idempotent), when a new job joins this queue (always on, not written in wake_on), on a wake_on event, every poll, and when a human chooses "Check again". One check per stage at a time; events during one cause one more after it; at least 5 s apart; its own job.held, job.admitted and job.escalated never wake it. A queue with no waiting job costs no check; a check over 5 minutes is killed and fails. It is allowed on the first stage too.
  • Where. In the pipeline's workspace (the shared checkout of its batches), from the folder's scripts/. A missing workspace or script fails the check visibly.
  • Input. PLAYBOOK_JOBS: JSON list of the stage's waiting jobs, oldest first, each { id, label, since, inputs } (all the job's own inputs; at most 100 jobs and 100,000 characters, the rest wait for a later check: PLAYBOOK_JOBS_OMITTED says how many), plus PLAYBOOK_STAGE, PLAYBOOK_PIPELINE, PLAYBOOK_RUN_ID, PLAYBOOK_STEP_ID, PLAYBOOK_CHECK and PLAYBOOK_WORKSPACE.
  • Result. Last stdout line, JSON: {"admit": ["job_a"], "hold": {"job_b": "QA not passed"}, "escalate": {"job_c": "dependency failed"}}. A job not named is held ("not admitted by the script"). Exit 75 or any failure changes nothing; a failure shows as an alert on the stage. Unknown ids are ignored with a warning.
  • Batches. A stage's next batch takes the oldest waiting job that is not held (fifo) or every one that is not held (merge); a held job never blocks the others. A job already in a batch is never held. A new job at such a stage starts held until its first check.
  • Escalation. escalate holds the job and opens a human ask on the pipeline run (kind admission, with jobId; in "Needs you", list_gates and get_run): Check again (retry), Withdraw the job (withdraw: it leaves, its hand-off ends failure) or Admit anyway (admit: it joins and the script no longer holds it). One ask per job at a time.
  • Events and view. job.held (only when the reason changes), job.admitted (via: script | human) and job.escalated. get_run lists each held job's reason; the panel's stage shows a "Held" badge and the reason, since when it waits, the last check, the next check countdown and the alert of a failed check.

Job events and the event log

A pipeline announces its jobs on the event bus (subscribe_events, list_events): job.queued (waits at a stage: handed off, or unlocked by a passed stage; one event per stage, via says which), job.joined, job.advanced (passed a stage; nextStages where it waits now), job.requeued (back at its stage: cause batch_failed with rides, retries, or outcome with outcome, reason, blocker, requeues), job.reopened (requeue_job put a failed job back; a job.queued with via: reopened follows), job.followup_pending (a batch ended while a detached job it settled with an outcome has no follow-up recorded) and job.followup (record_followup, or start_playbook with forJob, recorded one: followUpRunId, note), job.settled (left with an outcome), job.failed and job.withdrawn (reason), and, for a stage with queue.admit, job.held (reason), job.admitted (via, reason) and job.escalated (reason, gateId). Every payload has runId (the pipeline), playbook (the singleton's id), jobId, label, stage, batchRunId and outcome; a filter such as { playbook: release_trains, stage: stg } matches by equality, on any pipeline.

Details

The pipeline and its batches also keep an append-only log, <run id>.events.jsonl, next to the run file. The run file stays the source of truth; the log is checked against it. User config (config.yaml in the plugin data folder, read at start): event_core: { log: true, parity: warn }; log: false writes no log and checks nothing, parity: off only skips the check.

Example: subscribe_events

# subscribe_events arguments
{ "types": ["job.advanced", "job.settled"],
  "filter": { "playbook": "release_trains", "stage": "stg" },
  "delivery": "idle" }

# config.yaml in the plugin data folder
event_core: { log: true, parity: warn }

Sidekick

A project may have a Sidekick: a coordinator agent in a column beside the Playbooks screen, one tab per project. It is defined by a sidekick/ folder next to the playbooks. The folder never takes a playbook id: a playbook sidekick.yaml and sidekick/sidekick.yaml coexist. Without the folder the project has no Sidekick, and its tab offers Create the Sidekick files.

.paseo/plugins/playbooks/sidekick/
├── sidekick.yaml          # optional
└── instructions.md        # optional: the repository's rules for the Sidekick

sidekick/sidekick.yaml

sidekick:
  model: claude-opus-5-5
  watch: [gate.escalated, run.failed, run.manager_lost]

provider, model, mode, thinkingThe Sidekick agent's settings; without them it uses the managers' default.
watchEvent types (or globs such as gate.*) it is subscribed to, for this project's runs. Default: gate.escalated, run.failed, run.manager_lost.

The Sidekick runs in a hidden workspace on the project root. Its prompt forbids it to edit files or run commands itself, but its tools would allow it, so that rule is not enforced by the plugin. It sends subagents to change playbooks, and they open pull requests for you to merge. validate_playbooks checks both files.

Slow steps

A step that takes more than factor times the mean duration of its last runs completed runs (slow_warning, defaults 2 and 10, at least 3 samples) is flagged in the panel with a yellow triangle. Agents see the same rule on the server's whole run history: get_run gives a slow step slow: { elapsedMs, baselineMs, factor, ratio, samples, running } and the run slowSteps; list_runs rows have slowSteps, and list_runs { slow: true } lists only the runs with a step that is slow right now. subscribe_events type step.slow (stepId, elapsedMs, baselineMs, factor, ratio, samples) fires once when a running step first goes past the threshold, checked every 30 seconds.

Example: slow_warning

# defaults/main.yaml (a playbook's own slow_warning wins field by field)
slow_warning: { runs: 10, factor: 2 }

# subscribe_events arguments
{ "types": ["step.slow"] }

YAML pitfall

Inside a flow mapping ({ ... }), a comma ends the value. Quote text that contains a comma, or use block style:

outputs:
  changes: { type: string, description: "What you changed, per file" }
